# viber/agents - the coder, reviewer and arbiter task flow

What `task-coder`, `task-reviewer`, `final-reviewer` and `arbiter` pass to each other and what each may write while a task is built, reviewed, stalled or repaired. The dispatch side (when, at what tier) belongs to the skills node.

## Contracts

- Baseline report: `test-runner` writes `status: pass | skip | fail | build-failed` then `<test name> | <file> | <assertion or error>` lines; `task-coder` and `task-reviewer` treat a failure as pre-existing only when its test name and file match such a line.
- Red evidence: on a PASS of a `TDD: required` task with a task file, `task-coder` adds `RED: <n> failing | <log>` or `RED: missing <symbol> | <log>`, from a `Verification` run redirected into `red.log` before the first production edit, or, on an attempt starting with the production code in the tree and for a test green on its first run, into the next free `red-<n>.log` with the behaviour temporarily reverted, a test that does not fail alone there being deleted; a PASS whose own text admits skipping a required step is returned as `VERDICT: FAIL`. `task-reviewer` checks that the failing tests are the task's new ones; on `UNRUNNABLE` a new test that would pass on HEAD is a Blocking finding.
- Untested clauses: a `DoD` clause whose test `test-strategy.md` forbids counts as met by its code alone for `task-coder`, and `task-reviewer` blocks a `TDD: required` clause with no test only where the rules allow that test; a clause asking for a forbidden test still ends the coder on `VERDICT: FAIL` with its `DECIDE:` line.
- Integration tests: `task-coder` writes an integration test and never runs it, its `Verification` only listing or type-checking it (a `Repro:` test and the failing tests of a test-run report excepted), and a clause proven by one needs no red evidence; `task-reviewer` judges it by reading and blocks a test the task added that proves none of its `DoD` clauses.
- Extras: `task-coder` appends each path of its `EXTRA:` line to its `extras` file (`<id>-extra.md`) and `task-reviewer` to its own (`<id>-extra-review.md`), one repo-relative path per line; `task-reviewer` gets the coder's paths and the rechecks by running its `scope` command.
- Final-review slice: `final-reviewer` runs the `scope:` line of its dispatch, a `plan-index.sh --slice` call, and reads its `commit:` lines (its tasks' commits) and `file:` lines (its slice); a recheck carries `fix:` and no `scope:`.
- Suite run: `test-runner` selects the integration tests from `run-changes.sh`, writes its test command to a command file and runs the suite once through `run-suite.sh run`; `run-suite.sh wait` answering `NEXT: wait` is waited on again, never re-run.
- Stall path: `task-coder` writes its `DECIDE:` line whole to its `decide-file` (`<id>-options.md`) after finishing every `DoD` clause the dispute leaves untouched; on attempts 1 to 4 its options become `arbiter`'s `options:` for case `decide` at once, and the same coder is resumed by `SendMessage` with the `decision:` lines (ending `Continue the task under these decisions, then return your output lines again.`), in the same attempt and tier. A ruling reaches reviewers and `closeout` as a `decision: <task-id>: <text>` line of `status.md`, which wins over the task file. Every `DECIDE:` option is work the continuing coder or a later attempt does, or a ruling the build records; `arbiter`'s `## Actors` states what the orchestrator (writes and deletes no file, runs viber's scripts only) and a coder can do.
- Run lessons: a `run-lessons: <Name> x<n>, ...` coder dispatch line (left out on `lessons: none`) names the `test-strategy.md` rules this run's failed task reviews raised; `task-coder` reads them first and checks every test it writes against them before PASS, reviewers get none. `task-reviewer` spells a raised rule test-strategy `` `<Name>` `` (what `run-failures.sh --lessons` counts), lists every test of the task breaking it in one finding and keeps no test breaking a rule it raised.
- Scratch: `task-coder` keeps scratch output under its `out` directory and names a file it must leave in the tree outside `.temp/` on `SCRATCH:`, never also on `FILES:` or `EXTRA:`; `task-reviewer` blocks an untracked leftover with that line as the fix, never `rm`.
- Memory: with `memory` `true`, `final-reviewer` reports nothing living in a `CLAUDE.md`, a notes line about one included, and the final-review fix coder, handed `memory:` on its `review` dispatch, edits no `CLAUDE.md`.
- Repair pass: a `repair: <problem>` dispatch line makes `task-coder` fix that one problem on top of the task's earlier work, reading its notes and every `review-<id>-*.md` first, and `task-reviewer` gate that problem plus the task's whole `DoD`; `arbiter`'s case `cap` follows a failed repair pass. `closeout` returns `LEFT: <n>` (or `none`) after `PATH:` on `VERDICT: ARCHIVED`, the `left:` value of its `commit-task.sh --leftovers` call.
- Re-review: on every review after one of the task's reviews failed in the session (never before: a second round after a refused commit or in a resumed session carries none) `task-reviewer` gets `previous: <path>`, its last failed report, and checks that report's Blocking items first: one still standing ends the round on `VERDICT: FAIL` with those items alone, each first line copied character for character, and no full gate; one a `decision:` line overrules or the reviewer proves wrong is dropped, named as a Minor item; all fixed or dropped, or the file missing, it gates in full. `previous-review-prose.unit.test.ts` holds `implementor` and the agent together.
