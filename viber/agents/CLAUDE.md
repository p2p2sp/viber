# viber/agents - the twenty-nine subagents viber's skills dispatch

This directory owns one markdown file per agent registered in `viber/.claude-plugin/plugin.json` `agents[]`: each a single-purpose worker taking labelled lines and returning fixed lines. The dispatching side (what a skill sends, when, at what tier) belongs to the skills node; the reference files the agents read belong to the references node.

## Terms

- Labelled input: every agent's `## Input` names the `label: value` lines its dispatch carries and what each one means; a multi-line value (`input:`, `question:`, `summary:`, `brief:`) runs to the end of the prompt. The dispatching skill sends exactly those lines and nothing else.
- `refs:`: the plugin reference directory (`${CLAUDE_PLUGIN_ROOT}/references`), from which an agent reads the reference files its body names.
- Auditor agents: the four `code-auditor` agents (`mapper`, `scout`, `hunter`, `critic`). They take another form: a `# <Name> - <role>` heading, `## Inputs you are given`, `## Hard rules`, no tools paragraph, no `DENIED` line.
- Coder notes: `<run>/work/<task id>-coder.md`, the at-most-8-line notes `task-coder` writes, read as `*-coder.md` by `task-reviewer`, `final-reviewer`, `closeout`, `memory-writer`, `rules-writer` and `qa-writer`.

- Review set: `planner-spec-review` (reads the whole plan), `planner-graph-review` (reads from `## Tasks` on) and `planner-task-review` (a slice of at most 8 consecutive tasks, read from its `brief:` file in place of the plan) review a planner plan past 12 tasks, each gating only its own `plan-rules.md` sections; `planner-review` reviews every other plan. On a skeleton the first two run before the tasks are detailed and pass over a `PENDING` line.
- Planning agents: `plan-surveyor` (the outline of a change), `plan-architect` (the plan text, whole or as a skeleton, with its decision log), `plan-detailer` (the `Verification` and `DoD` lines of one slice of a skeleton) and `plan-fixer` (edit blocks for the plan). Each writes one file, which a script of `skills/planner/scripts/` reads; none writes the plan file.

## Relationships

- Reference reads: which agent reads which `<refs>/` file is listed per file in `references/CLAUDE.md`. `hunter` writes to the schema of `skills/code-auditor/references/synthesis.md`; `hunter` and `critic` get a clean checkout only for a lens reading `Worktree: required`, through `skills/code-auditor/scripts/worktree.sh` and, on the diff scope, `diff-overlay.sh`. `mapper`, `scout`, `hunter` and `critic` read the run file and one lens file of `skills/code-auditor/references/lenses/`; `mapper` also reads the `signals.md` that `skills/code-auditor/scripts/map-signals.sh` builds from that lens's `<lens>.signals.md`, and runs no signal command itself.
- Skill calls from agents: `prototype-writer` invokes `impeccable`, else `viber:pro-designer`, when either is in its skill listing.

## Contracts

- Strength: `task-coder` and `task-reviewer` get the task's tier as `model`, `final-reviewer` `sonnet` clamped into the tiers range, `scout` `sonnet` on the security lens; every other dispatch passes no `model`, so the frontmatter `model:` and `effort:` decide. `hunter` and `critic` carry `model: inherit` and run at the session's model; `mapper` is pinned to `sonnet`, `scout` to `haiku`. Of the planning agents `plan-surveyor` and `plan-detailer` are pinned to `sonnet`, `plan-architect` and `plan-fixer` carry `model: inherit`, all four `effort: high`; the four plan reviewers carry neither field.
- Every non-auditor agent carries the tools paragraph ("Only a call the harness refuses makes a tool unavailable: end your run then on `VERDICT: DENIED` ..."); an agent holding `Bash` adds the sentence that `No such tool available` on `Glob` or `Grep` means using `find` and `grep` through `Bash`, and `mapper`, `hunter` and `critic` state that fallback under `## Hard rules`. The same paragraph, and their hard rules for those three, add that a refusal whose reason opens with `viber guard:` is a correction to apply, never a denial.
- Agents sharing the working tree (`task-coder`, `task-reviewer`, `final-reviewer`) keep git read-only (`status`, `diff`, `log`, `show`), never `stash`, `checkout`, `restore` or `clean`: one stash stack serves every coder. `task-coder`'s only index writes are `git rm -r -q --` and `git update-index --chmod=+x --`. Each guarded rule is one line in the agent, enforced by `hooks/scripts/shell-guard.sh` (the coder: no chained command, no `rm`, no file write or inline or `.temp/` interpreter code through `Bash`, the four git subcommands; both reviewers: the git subcommands only; all three, and every other viber agent through the guard alone: no `cd` to a target holding a glob, a variable or a command substitution), whose header holds the rationale.
- Write scope: a reviewer or auditor writes only its report or findings file, and only on the verdict its `## Output` names (`task-reviewer` and `final-reviewer` write nothing on `PASS`; `planner-review` and the three review-set agents write their findings file on either verdict and none with no finding at all; `outside-plan-review`, `adr-screener` and `researcher` write nothing at all, `critic` nothing outside its reserved worktree but its `Out:` verdict file, `scout` only its `Out:` score file), except that `task-reviewer` also appends its `EXTRA:` paths to its `extras` file on either verdict; `arbiter` writes only its `ruling` file, the four output lines whole; `closeout` edits only `spec.md`, writes `outcome.md`, then makes one `commit-task.sh --leftovers` call (which rewrites `outcome.md` from its heading line on) before its one literal `archive-run.sh` call; `e2e-writer` writes one spec file plus its status line under `## Automation` of `qa.e2e.md`.
- Carrier rule: the four planning agents (`tools: Read, Grep, Glob, Write, Edit`) and the four plan reviewers (`Read, Grep, Glob, Write`) hold no `Bash` and write their result to the plan file the plan-mode notice names as theirs, with no such notice to their `out:` path, and to no other file. The reply is `OUT: <the path written>` on its own line, then the `VERDICT:` line (`MAPPED` for the surveyor, `WRITTEN` for the architect and the detailer, `FIXED` for the fixer, `PASS` or `FAIL` for a reviewer), and nothing else.
- A reply with no file: `plan-architect` and `plan-fixer` owing the user a decision reply `DECIDE: <decision> | <recommended option> | <option> | <option>` lines, then `VERDICT: DECIDE`; a reviewer with no finding at all replies `VERDICT: PASS` alone.
- Every planner dispatch block opens on `plan: <plan path>`: `scripts/run-summary.sh` counts a planning transcript only when its prompt names that path, so `plan-surveyor` carries the line without reading it. No reviewer reads its `sum:` line: `hooks/scripts/plan-gate.sh` reads it from the dispatch prompt.
- Plan review reads no scripted check: `planner-review`, `planner-spec-review`, `planner-graph-review` and `planner-task-review` read `plan-rules.md` only, so a check `plan-index.sh` decides (numbering, commit prefix, backticked or interpreter `Verification`, `CLAUDE.md` in `Files`, attachment names, template slots, scenario headings, a `modify` or `delete` file map path the tree lacks and, on a summary file input, its `Attachment:`, `Root cause:` and `Repro:` lines) stays out of their prompts. The first, second and fourth need only the callers of the symbols whose signature or observable behaviour the plan changes and the documents and `.claude/rules/` files naming a path it moves, modifies or deletes: the `reach:` file, or `## Reach` of the task reviewer's brief, holds that search already run, so each greps itself only for a symbol or path it lacks (the `Grounded` end-to-end spec search excepted) and reads a file only to confirm a hit or check a task against the code it modifies. `planner-graph-review` takes its callers from the reach file too and keeps its broad exploration, as `outside-plan-review` does.
- Join keys: `scout` echoes `unit` (the `U<n>` id) byte-identical to the unit line it was given; `critic` is handed only the `.claim.md` sidecar (`LOCATION`, `CLASS`, `## Reproduce`), never the hunter's report.

## Commands

- `node --test tests/viber/code-auditor.unit.test.ts` after an auditor agent is added, removed or renamed: it holds every `viber:<name>` the `code-auditor` skill dispatches to `plugin.json` `agents[]`.

## Change together

- The "Stop what you started" block is verbatim in `task-coder`, `task-reviewer`, `final-reviewer`, `test-runner`, `e2e-writer` and `skills/extension/templates/extension.md`.
- The tools paragraph and the `DENIED` / `REASON: <refused tool name>: <the exact refused command, or the path for a file tool>` / `REFUSAL: <the refusal text, on one line>` output wording are verbatim across every non-auditor agent (`researcher` adds the URL or query for a web tool).
- Memory audit vocabulary (`STALE`, `GONE`, `UNVERIFIABLE`, `MISS`, `SHAPE`, `OK`) and the `<out><slug>-audit.md` name (`/` -> `--`): `memory-auditor`, `memory-node-writer` and `skills/memory/SKILL.md`; `memory-auditor` copies each `shape:` line of its brief (the `memory-map.sh --targets` block) as a `SHAPE:` finding and judges only the title. The rules counterpart (adding `DROP` and `MOVE:`, and for the trail `IGNORED:`, `USED:`, `REJECTED:` in `<out>_trail-audit.md`): `rules-auditor`, `rules-writer` and `skills/rules/SKILL.md`. An `ENFORCE:` line (after the `AUDIT:` line) is no counter and never reaches a findings file or the writer: `rules-auditor` reports it. A rule matching no tracked file never reaches `rules-auditor`: `rules-map.sh --brief` writes its one `GONE:` line and `AUDIT:` line (`gone 1`) itself.
- The clean-checkout steps (`worktree.sh add`, `diff-overlay.sh`, replay, `worktree.sh remove`, and `WORKTREE_FAILED` / `OVERLAY_FAILED` ending in `NO FINDING` for `hunter` and `INCONCLUSIVE` for `critic`): `hunter.md` and `critic.md`.
- An agent added, removed or renamed: `plugin.json` `agents[]`, every `viber:<name>` dispatch in `skills/`, its line `id="agent-<name>"` in `skills/setup/assets/help.html`, and for `planner-review`, the three review-set agents and `outside-plan-review` `hooks/scripts/plan-gate.sh`. A planning agent or plan reviewer also has its `agent:` name printed by `lib/plan-build.ts` or the `dispatch:` lines of `scripts/plan-index.sh`, its role in the header and the `case` of `scripts/run-summary.sh` and its word cap in `tools/lint/data/caps.ts`.
- The labels of a review block (`plan:`, `refs:`, `memory:`, `input:` as a summary file path or text whose `Answered:` lines `skills/planner/SKILL.md` appends and the Faithful rule reads, `tasks: T<a>-T<b>`, `sum:`, `brief:`, `reach:`, `candidates:`, `previous:`, `fixes:`, `out:`): the four reviewer files and `skills/planner/scripts/review-round.sh`, whose header says which member gets which line. `hooks/scripts/plan-gate.sh` names `refs:`, `memory:`, `input:` and `tasks:` in the dispatch text of its deny messages and reads `tasks:` and `sum:` from the prompt.
- The labels of a writing block (`plan:`, `refs:`, `templates:`, `memory:`, `mode:`, `outline:`, `reach:`, `candidates:`, `tasks:`, `brief:`, `decisions:`, `findings:`, `gaps:`, `out:`, `input:`): the `## Input` of the four planning agents and `lib/plan-build.ts`, which prints them; `skills/planner/SKILL.md` appends the `add:` texts.
- The file each planning agent writes, its format held by the agent file and by the command of `lib/plan-build.ts` that reads it (the header of `skills/planner/scripts/plan-build.ts` names them): the outline (`plan-surveyor.md`, `outline`, read again by `plan-architect.md`), the architect file cut at `<!-- DECISIONS -->` (`plan-architect.md`, `skeleton`, its log the `decisions:` input of `plan-fixer.md`), the task file with its `GAP:` lines (`plan-detailer.md`, `merge`, the `gaps:` input of `plan-fixer.md`) and the fix file of `@@ EDIT` blocks and `fix:` lines (`plan-fixer.md`, `apply`, the `fixes:` input of the four reviewers).
- The reach targets (a path, `<path> | <symbol>`, `<path> | new`) and the candidates and paths files `lib/reach.ts` builds from them: `plan-surveyor.md`, the header of `plan-build.ts`, the `reach:` and `candidates:` inputs of `plan-architect.md` and the reviewers, and `## Reach` of a slice brief, which `plan-detailer.md`, `planner-task-review.md` and `plan-fixer.md` read.
- What `skills/planner/SKILL.md` appends to a fixer block and `plan-fixer.md` reads: the `FIX:` and `SPLIT:` lines of `plan-index.sh`, a `change:` block, and the `records:` block of `skills/planner/references/adr-tasks.md`, whose `rules:` line names that file for its `## Record tasks` and `## Record shape`.
- The `FIX:` lines of a refused file: a `plan-build.sh` exit 4 prints them, `skills/planner/SKILL.md` appends them to the next dispatch of the same block, and `plan-surveyor.md`, `plan-architect.md`, `plan-detailer.md` (`FIX: <range>: <defect>`) and `plan-fixer.md` (below `rejected:`) each write the whole file again.
- The tools paragraph, `## Calibration`, its re-review sentence and `## Output` are verbatim across `planner-review`, `planner-spec-review`, `planner-graph-review` and `planner-task-review`, and the three set agents take no `scope:` line. A re-review (a prompt carrying `previous:` and `fixes:`) checks only the text a `fix:` line changed and what refers to it, searching the code for nothing else. Their Blocking needs a finding verified in the plan or the code; a Minor finding that would be Blocking ends in `(inferred)` (unverified) or `(untouched)` (new on a re-review, outside the text a `fix:` line changed), the two suffixes `review-round.sh` prints as `MINOR:` lines for the user.
- The `(behaviour)` marker, on a Minor finding where the plan changes a behaviour today's code has that no acceptance criterion asks for: the `## Output` of the four reviewers, `review-round.sh` (a PASS whose findings file holds one counts as FAIL, once per member and plan, named on `behaviour:`) and `plan-fixer.md` (fixes it across its whole class in the plan).

- The guarded one-line rules of `task-coder`, `task-reviewer` and `final-reviewer`, and `hooks/scripts/shell-guard.sh` (rules R1-R6 and their rationale): a rule added or dropped changes both.
- The `viber guard:` marker sentence: the tools paragraph above, `mapper`, `hunter` and `critic` hard rules, `skills/extension/templates/extension.md`, and the marker `kill-guard.sh` and `shell-guard.sh` open their reasons with.

## Traps

- The four planning agents and the four plan reviewers each sit within 6 words of the cap `tools/lint/data/caps.ts` holds them to, `outside-plan-review` within 15: a word added fails the lint until the cap is raised on purpose.
- The harness rejects a subagent's `Write` of any `.md` whose name starts with `report`, `summary`, `findings` or `analysis`; `hooks/register.tsx` writes such a file in its place for a viber agent inside the project root, yet every file an agent is told to write is named otherwise (`outcome.md`, `review-*.md`, `*-audit.md`, the planner `out:` files `survey.md`, `architect.md`, `tasks-<range>.md`, `fix.md`). `findings-<k>.md` is the copy `review-round.sh` makes, never an agent's write.
- A planning agent in plan mode may write only the plan file the harness names for it, so its `out:` path under `.temp/viber/planner/` is used only outside plan mode: the session takes the path from the `OUT:` line, never from the block it sent.
- A file an agent writes that something parses (`hunter`'s report and sidecar, `mapper`'s `map.md`, `scout`'s scores, `critic`'s verdict, the four planning agents' files) can end on a leaked `</content>` line: no agent reads its tail back, the strip-tag core deletes it in the script that parses the file (`keep-units.sh`, `hunt-return.sh`, `plan-build.sh`), and a new parsed output needs the same call.
- `scout`, `mapper` and `hunter` return no `VERDICT:` line (`scores written: <path>`, `map written: <path>`, the paths written): a caller parsing them never looks for one, and for `hunter` reads the files in `reports/`, never its final message. `critic` ends on its `VERDICT:` line alone, yet the script reads the verdict file it wrote to its `Out:` path, never that message.
