# viber/lib - editing the plan and build cores

Read for a change to `plan-build.ts`, `plan-text.ts`, `plan-graph.ts`, `reach.ts`, a module of `plan-index/`, `task-ready.ts`, `run-notes.ts`, `file-guard.ts` or `archive-run.ts`. It covers how these cores read one plan and one run directory between them; what each prints lives in the header of its entry.

## Relationships

- `plan-build.ts` `runPlanBuild(argv, cwd, script, ports)` (`Fs`, `Git`, `Clock`) builds the plan of plan mode. It reads plan text with `parsePlan` of `plan-text.ts`, validates a candidate in process with `planDefects` and `templateSlots` of `plan-index/run.ts` before it writes anything, computes every `Depends-on` line with `plan-graph.ts`, searches the reach targets with `reach.ts` and sizes the files of a survey with `Fs.size`.
- `plan-text.ts` holds no port and no check: `parsePlan`, `linesOf`, `textOf`, `listOf`, the open items (`openItemsOf`, `withOpenItems`, `openItemLine`, `NOTE_CAP`, `FIXED_AFTER`, `sectionOf`), the cuts of an agent file (`cutFrame`, `frameSlicesOf`, `cutAuthor`, `cutSliceText`), the order and the numbering (`reorderTasks`, `mapTasks`, `renumberTasks`, `renameTaskIds`, `renameIn`, `renameTokens`, `withDepends`) and `slicesOf`, which `plan-index/final-review.ts` alone takes.
- `plan-graph.ts` `arrangeTasks(tasks, blockFiles, held)` answers the order in which each task follows the producer of what it uses, with the rings no order satisfies, `orderTasks(tasks, blockFiles)`, per task, the places of the earlier tasks it depends on, and `dependsValue(deps, ids)` the value of the line; it takes `namesPath` from `plan-index/check.ts`.
- `reach.ts` `collectReach(targets, root, git, candidatesFile)` (`Git.grep` alone) answers the candidates page and the paths page, a `| new` target on the first alone; `targetPath` is the path a target names.
- `plan-index/run.ts` `runPlanIndex(argv, cwd, script, ports)` (`Fs`, `Git`, `GitWrite`) is the one public entry of the plan-index core: it reads the call, resolves the config in process, and hands the plan to `read.ts` (one pass over the lines, the `## Open items` section included) and `check.ts` (the blocks together, the Verification command through `verification.ts`, the `--input` file through `input.ts`), then to one module per mode: `listing.ts` (the index, with `state.ts` for `status.md`), `scope.ts` (`--extra`), `dispatch.ts`, `slice.ts`, `final-review.ts` and `split.ts` (which ends a task file on the `## Notes` of its task). `text.ts` is how they all read plan text.
- `task-ready.ts` `runTaskReady(argv, cwd, ports)` (`Fs`, `Git.repoRoot`) reads the plan through `readPlan` of `plan-index/read.ts` with no check and the run through `readState` of `plan-index/state.ts`; `run-notes.ts` `runRunNotes(argv, cwd, ports)` (three reads of `Fs`) takes `openItemsOf` from `plan-text.ts`, `readPlan`, `readState` and `claims`, `repoPath` and `sequencedOf` from `task-ready.ts`.
- `file-guard.ts` `runFileGuard(payload, ports, { caseless })` (`Fs`, `Git.repoRoot`) reads `readState` and the task files of the run, never `plan.md`; its entry is `../hooks/scripts/file-guard.ts`, which hands it the whole stdin and sets `caseless` on darwin and win32 (the core asks no OS), so two spellings of one file compare as one path there.
- `archive-run.ts` `runArchiveRun(argv, cwd, ports)` (`Fs`, `Git`, `GitWrite`) reads the task ids and the settled ids with patterns of its own.

## Contracts

- `orderTasks` writes exactly the edges the three graph checks of `plan-index/check.ts` ask for (a shared `Files` path, a contract block consumed beside its writer, a file read in `Verification`, `Delivers` or `DoD` that an earlier task lists), then drops an edge reached through another. `arrangeTasks` first puts a task behind the first writer of a block it uses and behind the creator of a file it names, when neither stands before it: a plan `plan-build.ts` ordered and numbered passes those checks by construction, a ring of tasks excepted, which it reports as `FIX: cycle:`.
- `planDefects(text, opts)` answers the `FIX:` and `SPLIT:` lines `plan-index.sh` prints for a plan that never landed, with the `--input` checks when it is given the summary text, and reads no file itself.
- `withOpenItems` is the one writer of `## Open items`: critical items first, then at most `NOTE_CAP` notes per task with the `FIXED_AFTER` ones ahead, a note past the cap rewritten as a plan note naming its task, an item given twice kept once, no section for no item.
- `runFileGuard` never throws and prints nothing for every input it cannot read, so the edit goes on; it prints the one deny line only for a path another task on neither `done:` nor `skipped:` claims and the coder's own task does not, the path spelled as the claimant lists it.

## Change together

- The task block markers and the `- <Label>: <value>` field lines: `parsePlan` of `plan-text.ts`, `plan-index/read.ts`, the task id pattern of `archive-run.ts` and the first `- Files:` line `file-guard.ts` reads from a task file.
- An `## Open items` line (`- critical|note | <task id>|plan | <text>`): `openItemsOf` and `openItemLine` of `plan-text.ts` and `openItemOf` of `plan-index/read.ts`; the cap of 3 notes per task is `NOTE_CAP` there and the literal of the check in `plan-index/check.ts`. `plan-index/split.ts` and `run-notes.ts` number the notes of a task the same way, from 1 in section order.
- The dependency rules: `orderTasks` and the graph checks of `plan-index/check.ts`, which share `namesPath`.
- Who claims a path (the `Files` of a task plus its two extras files, `work/<id>-extra.md` and `work/<id>-extra-review.md`, until the task is done or skipped): `claims` of `task-ready.ts` (which `run-notes.ts` takes to name who listed a refused path), the copy in `file-guard.ts`, the refusal of `../scripts/commit-task.sh` and the `claimed` set of `plan-index/scope.ts` (`--extra`, the `Files` alone: it prints an extra path only a skipped task lists).
- The line `decision: <id>: sequenced after <other>: both need <path>`: the `SEQUENCED` pattern of `task-ready.ts` and the `--decide` text `../scripts/task-step.sh` prints.
- The planner work files under `.temp/viber/planner/`: the `WORK` pattern of `plan-build.ts` (every `.md` file, what a survey removes unless `--phase` goes on with the plan surveyed last, whose outline printed a split proposal) and the scratch list of `archive-run.ts` (the same pattern, the state file `plan-build`, and for the build `waits` and `guard`). A work file under another extension is removed by neither.

## Traps

- Two cuts are both called slices: the slices of a mapped change, cut by `plan-build.ts` from the areas of the survey (`SLICE_TASKS` 8, `SLICE_BYTES` 200000), and the slices of the final review, `slicesOf` (`ceil(n / 8)` runs of a landed plan's tasks). Neither reads the other.
- `runPlanBuild` rewrites the plan through `linesOf` and `textOf`: every write leaves each line ending on a line feed, a carriage return dropped, and the text cut from a frame or an author file loses the blank lines at both ends.
- `runPlanBuild` compares the plan path of a `survey --phase` with the one of its state file as text.
- `renumberTasks` numbers a task on the first `### <id> - <title>` heading of its block, and `plan-index/split.ts` names the task file after that one; the last such heading is the id `plan-index/read.ts` checks.
- `renameIn` renames a whole token only: a run of letters, digits, `_` and `-` that is no part of a path, so an `L<n>` inside a file name stays.
- `collectReach` skips a search term shorter than 3 characters (`skipped:`), drops a derived term of a whole-file target, and the directory of a `| new` target, whose hits span more than 25 files (`common:`), and keeps at most 200 hit lines per target (past them 2 per file) and 200 characters of each, counted in characters, never bytes; a target with an empty path gets no section.
- `plan-index/` reads a blank as an ASCII one and keeps a carriage return inside a line: `text.ts` holds the trim, the words and the line cut, never `\s` or `String.trim`. A byte that is no valid UTF-8 in the plan reaches `spec.md`, `phases.md` or a task file as U+FFFD.
- `runPlanIndex` hands its cwd, not the repository root, to every git call: the plan path is relative to it. A closing `<!-- /TASK -->` with no open block is ignored.
- `runRunNotes` takes its cwd as the repository root and resolves none: it is run from the root, as `commit-task.sh` runs and `run-summary.sh` inside a repository.
- `runFileGuard` keeps the task file it found in `<root>/.temp/viber/guard/<agent_id>` and reads no transcript again while that file names an existing task file.
- `runTaskReady` trusts `status.md` over its four lists: an id of `--flight`, `--held`, `--waiting` or `--lost` that is done or skipped is dropped, and an id of `--lost` that is also in `--flight` or `--held` is no lost task. Its `wait` mode reads a claimant missing from `--flight` as not running and puts the pair in sequence at once, so a caller always passes the flag.
