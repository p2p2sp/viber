# Plan rules

Every rule a plan must hold. A rule tagged `(script)` is rejected by `plan-index.sh`; a rule tagged `(review)` is the planner's own check before dispatch and is gated by the plan reviewer. The rules sit in four sections by role: `planner` and `planner-review` read the whole file; of the review set, `planner-spec-review` reads `## Spec` and `## Contracts`, `planner-graph-review` reads `## Graph`, `planner-task-review` reads `## Task`.

## Spec

- Split right: everything above `## Tasks` is WHAT and WHY - goal, problem, current behaviour, roadmap, scenarios, glossary, acceptance criteria, file map, boundary, constraints. A signature, type, endpoint, error code or dictionary key there belongs in a `## Contracts` block, the only way a shape reaches a coder. (review)
- Reach: a change to a rule other code also applies - the shared symbol itself, or how one caller applies it - puts every place applying it, directly or through to what a person observes, in `### File map`, and a `.claude/rules/` file or document naming a path, symbol or example file the change moves, deletes or leaves stale is such a place too; each one sits in some task's `Files` or under `### Out of scope` naming the behaviour it keeps. A place left in neither is a finding: a coder changes only its own `Files`, so that caller silently diverges. (review)
- Lean: everything the plan adds traces to an acceptance criterion or to a file `Reach` or `Owned` forces. A feature, option, parameter, configuration key or extension point no criterion asks for is a finding, and so is a new file, type or function with one caller and nothing to hide (deleting it would move no complexity, only remove a hop), a seam another rule requires (a port, an extracted pure function) excepted, or a task restructuring working code the criteria do not reach, splitting an unwieldy file the change must touch excepted. (review)
- Root cause: a plan built from a `viber:fixer` diagnosis, from code-auditor findings or from an input carrying a `Root cause:` line carries `## Root cause` above `## Acceptance criteria`, stating the cause the input names (for a `Root cause:` line, the cause that line names); a plan from any other input carries none, and a section there is a finding. (review)
- Tied: each acceptance criterion and each `### Edge cases` entry is tied to at least one task's done clause, a criterion several tasks cover proven by the union of their done clauses; an edge case is limited to behaviour the change introduces or changes, untouched behaviour belonging under `### Must not change`; a condition no single task delivers, like the suite staying green, is not an acceptance criterion but the build's own close. (review)

## Graph

- Ids: task ids are `T1`, `T2`, … in order. (review)
- Depends: `Depends-on` references lower-numbered tasks only, which keeps the graph acyclic. (script)
- Minimal: no `Depends-on` entry names a task already reached through another entry of the same line. (script)
- Ordered: `Depends-on` matches the actual flow of code and data - a dependency only where one task consumes what another produces, or where both write the same file. Every file, route or symbol a task's `Verification`, `Delivers` or a done clause reads that another task creates or changes needs that task among its `Depends-on`, directly or through another. A task needing something no listed dependency produces is a finding, and so is a dependency that constrains nothing: it burns parallelism. (review)
- Read after: a task whose `Verification` or `DoD` names a file a lower-numbered task's `Files` lists depends on that task, directly or through another. (script)
- Disjoint: tasks with no dependency path between them never list the same file, since they run at the same time. (script)
- Leaf: an Exclusive task is never named in another task's `Depends-on` - it runs last, so nothing may depend on it. (script)
- Shared harness: a plan touching the component or integration layer on a host with no harness for it designs one before slicing tasks - which dependencies it starts, one startup and schema shared by every test, how state resets, what runs in parallel, from the host's own test framework and the stack's in-process hosting that runs component tests from their entry point; a stack with no such hosting has no component layer. That harness lives in the `Files` of one task that is not `Exclusive`, which every task writing component or integration tests depends on; its `Verification` builds it without starting a dependency, and each consuming task adds only its own tests on top. A plan writing tests on a host declaring no layer marker convention or no fast command designs both from the test framework's native mechanism in its one harness task, created for this when the host already has a harness, and every task writing tests depends on it. An adapter task starting its own dependency, or two tasks each building a harness, is a finding. (review)
- Widened: a change that widens the set of values of a contract (an error code, a state, a variant) needs, for each consumer of that contract, a task whose done clause covers the consumer's handling of the new value, and that clause is proven by a test. A consumer with no such task is a finding: the new value reaches it unhandled, such as an error code shown as its raw key. (review)
- Sequenced: the plan-wide clauses moved out of four `## Task` rules, each kept in its own wording: from Size, a plan cut by layer where a behaviour slice was available is a finding, and the run's core lands in the earliest tasks as its smallest slice with its own unit or component proof, a core bound together with the work consuming it being a finding; from Owned, a shape two tasks need is written by the first one that cannot deliver without it, landing in a task of its own ahead of them when the task that would otherwise write it carries behaviour too, so its consumers wait for the shape, never for the behaviour; from Layered, where the adapter and its test form one `Exclusive: true` leaf task, its consumers reach it through a port or contract an earlier task writes; from End-to-end, a write-only end-to-end task depends only on the tasks whose routes, selectors or endpoints it reads. (review)
- Covers: every acceptance criterion is covered by at least one task's `Covers`, and every token there, written `AC<n>`, is an acceptance criterion. (script)

## Task

- Layers: a task's tests are `unit` (one unit, or several collaborating units with only input and output boundaries substituted), `component` (the whole application run in the test process from its own entry point, internal layers real, external adapters replaced by in-memory fakes holding their own state, never an in-memory database), `integration` (one adapter against its real dependency, started disposably for the test run; an entry point calling data access directly counts as the adapter), or `e2e` (the deployed application driven from outside, written and run only on the user's own request); an existing `e2e` spec a task's change breaks is updated inside that task and needs neither a unit or component test nor red evidence. (review)
- Size: each task is the smallest unit that carries its own verification and is worth a reviewer's gate; setup, config and docs fold into the task whose deliverable needs them. One behaviour per task: a task whose `Delivers` names behaviours a person can observe independently is split, one task each, and `plan-index.sh` refuses a `TDD: required` task past 12 `Files` or 6 `DoD` clauses and a `TDD: none` one past 25 or 10, so a shape the behaviour needs (entity, migration, registration) lands in a `TDD: none` task ahead of it; one behaviour runs through every layer it needs inside that task. (review)
- Title: the commit subject is `T<n> - <title>`, the heading line without its `###` marker and with no type prefix, so the title is one short imperative summary of what the task delivers. (review)
- Paths: `Files` is one comma-separated line of exact repo-relative file paths, no globs, no directories, no annotations, no quoting; a bracket wrapping a whole path segment (`[id]`, `[...slug]`, `[[...slug]]`) is part of the file's own name, written exactly as on disk. (script)
- Owned: `Files` is the task's complete map, staged for its commit and compared by the collision check: nothing outside it has to change for the task to deliver and pass its `Verification`. It holds every file the task's own work forces - where a new type is registered, exported or wired up, the declaration and migration a new persisted shape needs, a new port and test substitute for a database, queue, clock or network the behaviour touches, only where the host already uses ports for it, every existing test asserting the behaviour it changes, an end-to-end spec included, or a count, an enumeration or a snapshot over it, every link of the chain that would break a criterion's claim of absence (an import graph, a bundle's contents, a call never made) through today's tree, the test file proving each done clause. A contract on `File: none` whose shape plainly has a home is the same finding. (review)
- Exclusive: the `Exclusive:` line, when present, carries no value but `true`. (script)
- Exclusive: `Exclusive: true` only where a task cannot share the working tree or a machine-wide resource - a fixed port, one database, a suite that has to run alone - and the line left out everywhere else. A `Verification` hanging on such a resource without the marker is a finding, and so is the marker on a task needing nothing of the sort: it stops the whole build while it runs. (review)
- Hard: the `Hard:` line, when present, names its reason. (script)
- Hard: a task is settled for a coder making no design choice of its own - every edge, error path and state its work introduces is fixed by a done clause or a contract block it uses. Only a task whose design the plan cannot settle in advance (concurrency or ordering, security or cryptography, an algorithm whose correctness spans several modules, a migration of data already in use) carries `Hard: <that reason, one line>`, and the line is left out everywhere else. An unsettled choice on a task without the line is a finding, and so is the line on a task the plan could settle: it runs the task on the costliest model. (review)
- Uses: every task carries `Uses:`, naming existing contract blocks or `none`. (script)
- Supplied: `Uses` names every block the task's work touches, the ones it writes and the ones it only calls: the task file is the coder's whole input, so a shape left off reaches it nowhere. (review)
- Delivers: `Delivers` states WHAT the task produces, never how to code it, never a line number. (review)
- Provable: `Verification` is a runnable command plus the result that counts as proof, scoped to the task's own `Files` and the tests covering them; a whole-project suite run is a finding, since other tasks write the same tree at once. A `Verification` command wrapped in backticks is a finding: it is written bare, as the task template shows, because `red-check.sh` runs the text as it stands. A `Verification` running inline interpreter code (`python -c`, `node -e`, `ruby -e`, `perl -e`) or a script under `.temp/` is a finding: the coder's shell refuses both, so the proof is the project's own test or script command. A task with no runtime behaviour greps its artefact for an identifier the code really declares, on both sides in one command - the document and the source file defining the identifier. A `Verification` a plausible invention would satisfy is a finding: a grep for a word, a document-side check with nothing on the code side, "read it and judge". A decision record under `docs/adr/` is proven by its own file and its `Status:` line, with no code side, and names from the code only `### File map` paths and `## Contracts` block names: any other code identifier in it is a finding. `DoD` separates its clauses with semicolons, each observable on its own, because each is cut into `DoD.1`, `DoD.2`, … and gated alone, and lists them in build order, innermost layer first (domain, then adapter, endpoint, interface), because the coder works them in that order, one red-green cycle each. Any wording that hands a clause's proof to another task, not only naming its id, is the same finding as `Self-proven`. On `TDD: required`, every done clause is provable by a unit or component test inside the task's own `Files`, that test file among them, or, for a clause only the real dependency reveals, the adapter's own integration test inside the same task. The test proving each done clause runs inside the task's `Verification` command, a write-only end-to-end task excepted, whose clauses the End-to-end rule proves without running the test, an existing end-to-end spec update excepted as well: the End-to-end rule proves it without running it. (review)
- Consistent: a task's done clauses, `Delivers` and `Covers` agree with every contract block its `Uses` names - the same variant names, error codes and sets of states, no clause narrowing or contradicting what the block already declares. (review)
- TDD: `TDD: required` by default. `TDD: none` only on a task that changes no runtime behaviour (config, docs, mechanical rename, scaffolding); delivers something with no decision inside it (a data shape, an accessor, a trivial constructor, a re-export, a registration, a 1:1 mapping, a constant table); carries `Repro:` (Reproduced); writes or runs an end-to-end test (End-to-end); or belongs to a host with no test layer (no test tooling, or nothing with runtime behaviour to assert), whose tasks verify artefacts, name the boundary unproven and never add a test framework. A task whose behaviour only a component test could observe on a host with no component layer (a stack with no in-process hosting that runs component tests from their entry point, the `Shared harness` rule's sense) is `TDD: none` as well: its `Verification` is a grep on both sides, the source declaring the identifier and the place consuming it, and any decision logic inside it is extracted into a pure function that a `TDD: required` task proves. An existing end-to-end spec listed in a task's `Files` leaves that task's `TDD` as it is and needs no red evidence. (review)
- Reproduced: a `Repro:` path is one of the same task's `Files`, and the task carrying it is `TDD: none`. (script)
- Reproduced: a reproduction test already RED in the tree is in the fixing task's `Files` and on its `Repro:` line; a bug-fix plan missing that line is a finding, since without it the build reads the uncommitted test as an interrupted coder. (review)
- Self-proven: a `DoD` clause naming another task of the same plan, outside backticks, is a finding; `plan-index.sh` rejects it. (script)
- Layered: a unit or component test needing a real database, queue, broker or network is a finding - that behaviour belongs behind a seam, proven instead by the adapter's own integration test. The adapter task stays `TDD: required`, its data-access clauses proven by that integration test, which runs only the adapter's own tests and carries no `Exclusive` when the dependency is disposable on a random port; only on a fixed shared resource do the adapter and its test form one `Exclusive: true` leaf task. (review)
- End-to-end: an existing end-to-end spec whose selector a task changes sits in that task's `Files` and needs no criterion, proven inside its `Verification` by the test tool's type-check or listing step plus a grep of the new selector on both sides, the spec and the source declaring it, and never run. A new end-to-end test - a browser, or the running application driven from outside - appears in a criterion, task or `Verification` only under an acceptance criterion stating that the user asked for one in their own words. By default that task only writes it: `TDD: none`, no `Exclusive`, its `Verification` never executing the test but running the test tool's own listing or type-check step plus a grep of one route or selector on both sides, the test and the source declaring it; its done clauses are proven by that listing step and grep, never by running it. Only a criterion stating the user asked for it to be run, in their own words, makes it an `Exclusive: true` task, `TDD: none`, its `Verification` running the test itself. (review)
- Memory-owned: with the `build.memory` switch on, no task lists a `CLAUDE.md` in its `Files`, whatever the host's own instructions ask, no exception, the root `CLAUDE.md` included. The nodes below the root belong to the build's close alone; the root is the user's file, and a change to it reaches the user only as the close's `SUGGEST:` line. (review)
- Covered: each task really delivers what the criteria its `Covers` names require, each covered criterion tied to one of its done clauses; a done clause proving nothing in `Covers`, `Delivers` or an edge case is a finding. (review)

## Contracts

- Blocks: one `### C<n> - <name>` block per shape the change introduces or consumes, ids `C1`, `C2`, … in order, under the `## Contracts` appendix below the tasks; a change introducing no shape has no appendix and every task carries `Uses: none`. (review)
- Block body: a block opens with a `File:` line. (script)
- Block body: `File:` names the repo-relative paths the shape is declared in, or `none` for one living in no file of its own, then the shape itself and nothing else: no rationale, no history, no instruction on how to build it. (review)
- Glossary: a `## Glossary` term the code has to name - an identifier, a field, a state or a value a coder writes - gets its own block, named by the `Uses` of every task that writes or reads it; `File: none` fits a term living in no file of its own. (review)
- Named: every block is named by at least one task's `Uses`. (script)
- Writer: the plan never says which task writes a block and which only calls it: the task whose `Files` holds the block's own file writes it, every other one takes it exactly as written. (review)
- Homed: every `File:` path is in some task's `Files` unless the tree already holds it. (script)
- Seen: at least one task holding a block's `File:` path names that block in its `Uses`. (script)
- Consumed after: a task naming a block in `Uses` depends, directly or transitively, on every lower-numbered task holding that block's `File:` path and naming it in its own `Uses`. (script)
