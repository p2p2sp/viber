# viber/references - shared rule and format references read at runtime

The eleven markdown files viber skills and agents read by path while they work: the plan rules (the rules a writer of the plan holds its text to and the scripted ones apart), the test rules, the TDD cycle, the admission gates for decision records and `.claude/rules/`, the node doctrine, the QA document formats, the issue save steps and the UI tells checklist. No script parses them: each is prose a model holds itself to, so its wording is its contract. Skill-private references live under `skills/<skill>/references/`, never here.

## Relationships

- A skill reads a file as `${CLAUDE_PLUGIN_ROOT}/references/<file>`; an agent reads it as `<refs>/<file>`, `refs:` being the `${CLAUDE_PLUGIN_ROOT}/references` line its dispatching skill passes.
- Readers per file:
  - `plan-rules.md` and `plan-rules-script.md`, each by range (`Grep` for the `## ` lines, then `Read` the section): `plan-architect` `## Spec`, `## Graph` and `## Contracts`; `plan-author` `## Task`, and both files whole when it writes a whole plan. `plan-surveyor`, `plan-judge` and `outside-plan-review` read neither.
  - `integration-tests.md`: `plan-author` for a task writing an integration test or creating or changing an adapter; `task-coder` and `task-reviewer` on a task writing or running one, creating or changing an adapter, or building the shared harness.
  - `test-strategy.md`, read by range (`Grep` for the `## ` lines, then `Read` the section): `plan-author` `## Layers`, `## Proves` and `## Ports`; `task-coder` whole, before its first test; `task-reviewer` `## Layers`, `## Proves` and `## Writing` (plus `## Ports` when the task's `Files` hold a port, its fake or its contract test) when the work touched tests or a fixture, and `## Ports` alone when the work reaches an external dependency; `fixer` `## Layers`, `## Proves` and `## Writing` before its reproduction test; `hunter`, and `critic` on the tests lens, `## Proves` and the `Boundary` line, through the `Test rules:` line of their briefs.
  - `tdd.md`: `task-coder` on a `TDD: required` task, before its first line of production code.
  - `qa-format.md`: `qa-writer` (writes `qa.md` and `qa.e2e.md`) and `e2e-writer` (reads one entry, writes its `## Automation` line).
  - `adr-admission.md`: `adr-screener`, dispatched through `skills/planner/references/adr-tasks.md` when `planning.adr` is on.
  - `rule-admission.md`: `rules-writer` and `rules-auditor`; it bars a `.claude/rules/` line asking for a test `test-strategy.md`'s `(blocking)` rules forbid.
  - `node-doctrine.md`: `memory-writer`, `memory-node-writer` and `memory-auditor` (its `## Template` part, for the title's `SHAPE` finding alone: the heading findings are the `shape:` lines `memory-map.sh` prints and the auditor copies).
  - `ui-tells.md`: `task-coder` and `task-reviewer` on a task whose `Files` render or style an interface; the short form of `skills/pro-designer/references/anti-slop.md`, which `pro-designer` reads in full.
  - `issue-save.md`: `issue-create` and the fragments `skills/fixer/fragments/issues-save.true.md` and `skills/intent/fragments/issues-done.true.md`, each passing `directory:`, `eligible:` and `content:` (an issue set: `parent:` and `parts:` in place of `content:`).

## Contracts

- `plan-rules.md` holds only `(review)` rules, ones the writers of the plan hold their text to and no script checks; `plan-rules-script.md` holds every `(script)` rule, one `scripts/plan-index.sh` rejects with the `FIX:` text the rule quotes, as `plan-build.sh assemble` and `apply` do in process. A rule tagged `(script)` with no matching check in `lib/plan-index/check.ts` is enforced by nobody. No reviewer reads either file: `plan-judge` holds its one rule for what is critical in its own body.
- A rule ending in `(blocking)` in `test-strategy.md` or `integration-tests.md` is a Blocking finding for `task-reviewer` and binds `task-coder` and `fixer`; an untagged rule is guidance only.
- `test-strategy.md` is the one definition of the test layers and of the tests that may be written: named rules (`Public`, `State`, `Source`, `Earned`, `Boundary`, `Ported`, `Proof`...) in the four `## ` sections `Layers`, `Proves`, `Ports`, `Writing`, which readers cite by name and read by range, so a renamed section or rule breaks those reads. `plan-rules.md` and `tdd.md` point at it and define none of it.
- `plan-rules.md` sits in four `## ` sections, `Spec`, `Graph`, `Task`, `Contracts` (`plan-rules-script.md` in the same four): the frame owner reads three and the author of a slice `## Task` alone, each by the `## ` line numbers it greps, so a rule belongs to the section of the writer who can hold its text to it, and a section renamed breaks those reads and the `Task` section of `cap/plan-author-read-set`. `Ordered` sits in `## Task` for that reason: only an author can name the file its task reads.
- `build.memory` reaches `plan-rules-script.md`'s `Memory-owned` rule through `plan-index.sh` and `plan-build.sh`, each resolving the config itself; `plan-architect` and `plan-author` receive it as their `memory:` line (`false` when missing) only for `plan-rules.md`'s `Provable` grep exclusion.
- `issue-save.md` consumes the `STATUS=ready` block of `scripts/issue-templates.sh` and calls `scripts/issue-create.sh` as one literal line, reading its exit codes 0, 1, 2 and its `TYPE=dropped|error` and `PARENT=error` lines. Every preview shows the path of a body file already written, never the body text.

## Change together

- Memory budgets (4000 root, 12000 per node and section, 32000 per chain): `node-doctrine.md`, `lib/memory-map.ts` (`ROOT_BUDGET`, `NODE_BUDGET`, `CHAIN_BUDGET`; the header of `skills/memory/scripts/memory-map.ts` names them), `skills/memory/SKILL.md`, `agents/memory-node-writer.md` (the root's 4000), `README.md` and `tests/viber/lib/memory-map.unit.test.ts`.
- The `## Template` heading list and order of `node-doctrine.md` and `HEADINGS` in `lib/memory-map.ts`, which judges headings, with `agents/memory-auditor.md`'s `## Shape`.
- The test layers: `test-strategy.md`'s `## Layers` defines them, `integration-tests.md` holds the integration layer's own rules, `plan-rules.md`'s `Layers`, `Layered`, `Observable`, `Owned`, `Shared harness` and `TDD` cite them by rule name; `PRODUCT.md` names the same four layers.
- The test rules (a use case's decisions are proven by a component test on fakes; every dependency sits behind a port with one fake and a contract test; an integration test is written in its task, never run there and run once by the final test run; a test only for a critical path or a decision in the logic, an edge case only where it flips a decision's outcome, one test per regression, one behaviour per unit test, every outcome of one act asserted together in a component or integration test, no arrangement and act repeated per assertion, an existing component or integration test already making them extended before a new one is written, none for a default value, a name, a data shape or what a user interface renders, whose decision is proven in the reducer, state machine or function holding it; a done clause whose test the rules forbid proven by its code alone, one asking for such a test a finding; done clauses ordered main path first, then one decision each; a test green on its first run kept only if it alone fails once the behaviour is reverted; a clause proven through an entry tests already call before a new one): `test-strategy.md`, `plan-rules.md`'s `Layered`, `Observable`, `Provable`, `TDD`, `Mockup`, `Size` and `Owned`, `integration-tests.md`, `tdd.md` (the cycle only), `rule-admission.md`, `agents/task-coder.md`, `agents/task-reviewer.md`, `agents/test-runner.md`, `agents/hunter.md`, the `over-mocking` and `wasteful-tests` angles of the `tests` lens, the `untestable-decisions` angle of the `design` lens, and the guides (`PRODUCT.md`, `README.md`, `help.html`); `tests/viber/test-pyramid-prose.unit.test.ts` pins the prose of the reference and agent files, `lenses.unit.test.ts` the lens angles, `rules-trail-prose.unit.test.ts` `rule-admission.md`.
- The read sets of `plan-author` (its file, `## Task` of both plan rule files, `skills/planner/templates/tasks.md` and three sections of `test-strategy.md`), `task-coder`, `task-reviewer` and `hunter` (their files plus the sections above): the rules `cap/plan-author-read-set`, `cap/task-coder-read-set`, `cap/task-reviewer-read-set` and `cap/hunter-read-set` of `tools/lint/data/caps.ts` cap each in bytes, so a line added to one of those files, or to a section they read, needs room there.
- `tests/viber/replay/done-clauses.md`: the sample of done clauses a plan author must not write or may write and a coder proves with or without a test, kept beside the `Observable` rule and `Proves` rules it exercises.
- The end-to-end rule (written only when the user asked in their own words, run only when they asked for a run, except an existing spec whose selector a task changes, which joins that task's `Files`, is type-checked or listed plus a grep of the new selector on both sides and never run): `plan-rules.md`'s `End-to-end`, `Layers`, `TDD`, `Owned`, `test-strategy.md`'s `Requested` rule, `agents/plan-author.md` and the hand-off line of `skills/planner/SKILL.md`.
- `plan-rules-script.md`'s `Provable` rule bars a `Verification` running inline interpreter code or a `.temp/` script: the coder's `shell-guard.sh` (R5) refuses both.
- `issue-save.md` step 6 and the argv and exit contract in the header of `scripts/issue-create.sh`.
- `ui-tells.md` and `skills/pro-designer/references/anti-slop.md` keep the same `##` sections; `ui-tells.md` stays within 4096 bytes and names nothing of pro-designer's context (`tests/viber/ui-tells.unit.test.ts`).
- `qa-format.md`'s `qa.e2e.md` headings and `## Automation` lines and the ID handling of `skills/e2e/SKILL.md`, which lists IDs from `## UI scenarios` / `## API scenarios` and skips `## Not automatable`.

## Traps

- `plan-rules.md` and `plan-rules-script.md` carry some rule names twice (`Title`, `Hard`, `Supplied`, `Provable`, `Layered`, `Reproduced`, `Blocks`...): one half `(script)`, the other `(review)`. Editing one never removes the other.
- `test-strategy.md` is capped at 7170 bytes (its `Layers` + `Proves` + `Ports` at 4200) in `test-pyramid-prose.unit.test.ts` and the `tests` lens at 9000, with 70 bytes of room in the file, 2 in `Layers` + `Proves` + `Ports` and about 140 in the lens: a rule added to one needs another cut; `plan-rules.md` is capped there at 20900.
- `plan-author` reads `## Task` of both plan rule files once per slice of a plan and again on each fix of its text, and both files whole when it writes a whole plan: a sentence added to `## Task` is paid once per slice.
