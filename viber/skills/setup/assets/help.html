Getting startedPierwsze kroki#

Four things, in this order: install the plugin, prepare the project, tell viber how your project builds and tests, then take one change from idea to commit.

Cztery rzeczy, w tej kolejności: zainstaluj wtyczkę, przygotuj projekt, powiedz viber, jak twój projekt się buduje i testuje, a potem przeprowadź jedną zmianę od pomysłu do commita.

1. Install1. Instalacja#

In a terminal:

W terminalu:

claude plugin marketplace add https://github.com/p2p2sp/viber --scope user
claude plugin install viber@p2p2 --scope user

Other ways to install, optional tools and updates: Install options and updates.

Inne sposoby instalacji, narzędzia opcjonalne i aktualizacje: Instalacja: opcje i aktualizacje.

2. Prepare the project2. Przygotowanie projektu#

Open Claude Code in your project and run /viber:setup. It sets up viber's config, permissions and ignore rule, and tells you when CLAUDE.md lacks what step 3 needs, or does not exist and /viber:memory must write it.

Otwórz Claude Code w swoim projekcie i uruchom /viber:setup. Ustawia konfigurację viber, uprawnienia i regułę ignorowania, a także mówi, czego w CLAUDE.md brakuje do kroku 3 albo że pliku nie ma i /viber:memory musi go napisać.

3. What CLAUDE.md must state3. Co musi podawać CLAUDE.md#

viber knows nothing about your stack. Every agent takes the build and test commands from this project's own instructions, so without them test-runner guesses from whatever manifest it finds, and a task can be committed on a suite that never ran.

viber nic nie wie o twoim stosie technologicznym. Każdy agent bierze polecenia budowania i testów z instrukcji tego projektu, więc bez nich test-runner zgaduje na podstawie manifestu, który akurat znajdzie, a zadanie może zostać zacommitowane na testach, które nigdy się nie uruchomiły.

No CLAUDE.md yet: run /viber:memory, which writes a short root once, within 4000 bytes, holding the items below. From then on the root is yours: no build or review rewrites it, and the changes they would make to it arrive as suggestions for you to apply. With a root already there, make sure it states the items below. /viber:setup checks the first five and, when one is missing, gives you a prompt to paste into Claude.

Nie masz jeszcze CLAUDE.md? Uruchom /viber:memory: jednorazowo napisze krótki główny plik, w granicach 4000 bajtów, z poniższymi punktami. Od tej chwili plik jest twój: żaden build ani przegląd go nie przepisuje, a zmiany, które by w nim zrobiły, dostajesz jako sugestie do samodzielnego wprowadzenia. Gdy główny plik już jest, upewnij się, że podaje poniższe punkty. /viber:setup sprawdza pierwsze pięć i, gdy któregoś brakuje, daje ci prompt do wklejenia do Claude.

  • the exact build command;dokładne polecenie budowania;
  • the exact test command;dokładne polecenie testów;
  • how to run a single test file;sposób uruchomienia pojedynczego pliku testów;
  • the exact fast command: a test command that runs every test but the integration and end-to-end ones;dokładne szybkie polecenie: polecenie testów, które uruchamia każdy test poza integracyjnymi i end-to-end;
  • the layer marker convention: how a test is tagged with its layer (unit, component, integration or e2e), such as a marker, trait, tag, build tag, runner project or file-name pattern;konwencja znaczników warstw: jak test jest oznaczany swoją warstwą (unit, component, integration albo e2e), na przykład znacznik, trait, tag, build tag, projekt runnera albo wzorzec nazwy pliku;
  • whatever else a newcomer would get wrong, such as how to launch the app, the required env or the migrations.wszystko inne, co nowa osoba w projekcie zrobiłaby źle: jak uruchomić aplikację, jakich zmiennych środowiskowych potrzeba, jak wykonać migracje.

4. One change, from idea to commit4. Jedna zmiana, od pomysłu do commita#

  1. /viber:intent add CSV export to the reports page

    /viber:intent eksport CSV na stronie raportów

    The interview asks only what your words and the code leave open, one question at a time, each with three options and its recommendation first. It ends on a summary you confirm.

    Wywiad pyta tylko o to, czego nie rozstrzygają twoje słowa i kod, jedno pytanie naraz, każde z trzema opcjami i rekomendacją na pierwszym miejscu. Kończy się podsumowaniem, które potwierdzasz.

  2. You approve the planZatwierdzasz plan

    The planner takes the summary into Claude Code's plan mode and writes the plan: acceptance criteria, a file map, then the tasks. planner-review checks it against your code, and plan mode ends only after that review passes. A plan past 12 tasks is checked by planner-spec-review, planner-graph-review and planner-task-review at once, and plan mode ends only when all of them pass. Then you approve the plan or reject it.

    Planista przenosi podsumowanie do trybu planowania Claude Code i pisze plan: kryteria akceptacji, mapę plików, a potem zadania. planner-review sprawdza go na twoim kodzie, a tryb planowania kończy się dopiero wtedy, gdy ta recenzja przejdzie. Plan powyżej 12 zadań sprawdzają jednocześnie planner-spec-review, planner-graph-review i planner-task-review, a tryb planowania kończy się dopiero wtedy, gdy przejdą wszyscy. Wtedy zatwierdzasz plan albo go odrzucasz.

  3. You ask Claude to build itProsisz Claude o zbudowanie

    The build copies the plan into docs/_specs/<stamp>_<slug>/, hands each task to task-coder, has task-reviewer check it where a review is due, and commits each task on its own, titled T1 - <task title>.

    Build kopiuje plan do docs/_specs/<stamp>_<slug>/, każde zadanie zleca task-coder, tam, gdzie należy się recenzja, oddaje je do sprawdzenia task-reviewer i każde zadanie commituje osobno, z tytułem T1 - <tytuł zadania>.

    It runs to the end without a person at the keyboard: where it would otherwise stop and ask, the arbiter rules, and every ruling lands in rulings.md.

    Idzie do końca bez człowieka przy klawiaturze: tam, gdzie inaczej zatrzymałby się i zapytał, rozstrzyga arbiter, a każde rozstrzygnięcie trafia do rulings.md.

  4. The build closesBuild się zamyka

    The fast tests and the integration tests the change reaches run, then the close parts your switches turn on. With the template's defaults, what the build taught goes into CLAUDE.md nodes below the root and .claude/rules/, changes to the root arrive as suggestions, and the run is archived in docs/specs/.

    Uruchamiają się szybkie testy i testy integracyjne, których dotyka zmiana, a potem te części zamknięcia, które włączają twoje przełączniki. Przy domyślnych ustawieniach szablonu to, czego nauczył build, trafia do węzłów CLAUDE.md poniżej głównego pliku i do .claude/rules/, zmiany w głównym pliku dostajesz jako sugestie, a przebieg ląduje w archiwum w docs/specs/.

A bug takes the same path, starting from /viber:fixer in place of the interview.

Błąd przechodzi tę samą drogę, tyle że zaczyna od /viber:fixer zamiast od wywiadu.

This is one path. The map of the whole flow shows the others: a mockup first, the fast path and Claude Code's own plan mode.

To jedna ścieżka. Pozostałe pokazuje mapa całego przepływu: najpierw makieta, szybka ścieżka i zwykły tryb planowania Claude Code.

Add a featureDodaj funkcję#

For a change that needs a plan. A small change you want made right away needs none: ask Claude for it directly and say you want it without a plan. A small change to existing code you still want designed first takes the fast path: the same command ends on a short design in chat, and Claude builds it in your session once you say yes, with no plan file.

Dla zmiany, która potrzebuje planu. Mała zmiana, którą chcesz mieć od razu, planu nie wymaga: poproś o nią Claude wprost i powiedz, że ma ją zrobić bez planu. Mała zmiana istniejącego kodu, którą chcesz najpierw zaprojektować, idzie szybką ścieżką: to samo polecenie kończy się krótkim projektem na czacie, a Claude buduje zmianę w twojej sesji, gdy powiesz „tak”, bez pliku planu.

  1. You typeWpisujesz

    /viber:intent let admins deactivate a user account

    /viber:intent pozwól administratorom dezaktywować konto użytkownika

  2. viber doesviber robi

    The interview asks what your words and the code leave open, one question at a time, and ends on a summary you confirm. planner writes the plan in plan mode and planner-review checks it (a plan past 12 tasks goes to the planner-spec-review, planner-graph-review and planner-task-review set instead). Once you approve it and ask Claude to build it, implementor builds and commits one task at a time.

    Wywiad pyta o to, czego nie rozstrzygają twoje słowa i kod, po jednym pytaniu, i kończy się podsumowaniem, które potwierdzasz. planner pisze plan w trybie planowania, a planner-review go sprawdza (plan powyżej 12 zadań trafia zamiast tego do zestawu planner-spec-review, planner-graph-review i planner-task-review). Kiedy plan zatwierdzisz i poprosisz Claude o jego zbudowanie, implementor buduje go i commituje zadanie po zadaniu.

  3. What is leftCo zostaje

    One commit per task, titled T1 - <task title>. With the template's defaults the build also updates the CLAUDE.md nodes below the root and .claude/rules/, suggests changes to the root without making them, and archives the run in docs/specs/.

    Po jednym commicie na zadanie, z tytułem T1 - <tytuł zadania>. Przy domyślnych ustawieniach szablonu build aktualizuje też węzły CLAUDE.md poniżej głównego pliku i .claude/rules/, zmiany w głównym pliku tylko sugeruje, a przebieg odkłada do archiwum w docs/specs/.

Large requests, drafts and small plansDuże prośby, szkice i małe plany
  • A request too large for one plan (over about 30 tasks) gets a proposed split into ordered parts first, a mechanical cut, never a release of its own, and every part holds at least about 8 tasks. Every part is interviewed up front and each gets its own cycle; the later parts' decisions are kept in roadmap.md, and a finished build names the next part. With GitHub issues on, each part gets its own sub-issue under one parent issue, and a part that resumes is tied to its sub-issue. The planner checks the size too: when its plan grows past 30 tasks, it asks whether to split through the interview or keep one plan, and it asks every decision its exploration finds that the interview left open.Prośba zbyt duża na jeden plan (ponad około 30 zadań) najpierw dostaje propozycję podziału na uporządkowane części, czysto mechanicznego, nigdy osobnego wydania, a każda część ma co najmniej około 8 zadań. Wywiad obejmuje każdą z nich, a każda przechodzi własny cykl; decyzje późniejszych części zostają w roadmap.md, a zakończony build wskazuje następną część. Przy włączonych zgłoszeniach GitHub każda część dostaje własne zgłoszenie podrzędne pod jednym zgłoszeniem nadrzędnym, a wznawiana część jest związana ze swoim zgłoszeniem podrzędnym. Rozmiar sprawdza też planner: gdy jego plan przekroczy 30 zadań, pyta, czy podzielić zmianę przez wywiad, czy zostawić jeden plan, i pyta o każdą decyzję, którą znajdzie w swoim badaniu, a której wywiad nie rozstrzygnął.
  • /viber:intent --prove let admins deactivate a user account has prover check the claims of every question against the code before you see it./viber:intent --prove pozwól administratorom dezaktywować konto użytkownika zleca agentowi prover sprawdzenie w kodzie twierdzeń każdego pytania, zanim je zobaczysz.
  • Others must read the specification before any task is planned: ask during the interview to stop at a specification. The draft lands in docs/_specs/<stamp>_<slug>/plan.md for you to commit and circulate, and /viber:intent pointed at that draft continues it. A build refuses a draft.Inni muszą przeczytać specyfikację, zanim powstaną zadania: poproś w trakcie wywiadu o zatrzymanie się na specyfikacji. Szkic trafia do docs/_specs/<stamp>_<slug>/plan.md, skąd go commitujesz i rozsyłasz, a /viber:intent wskazujący ten szkic prowadzi go dalej. Build odmawia zbudowania szkicu.
  • For a small, well understood change Claude may suggest its own plan mode instead of the interview. With planning.plain-plan-review on, that plan still has to pass a review before plan mode ends.Przy małej, dobrze zrozumianej zmianie Claude może zaproponować zwykły tryb planowania zamiast wywiadu. Przy włączonym planning.plain-plan-review taki plan też musi przejść recenzję, zanim tryb planowania się skończy.
  • With planning.fast-path on, the interview sends a change to existing code of at most 2 tasks with code and 5 in total, with no new subsystem, restructuring or domain concept, down the fast path: a short design in chat, built in your session after your explicit yes, proven by test-runner, with no plan file and no run directory. A correction gets a revised design; ask for a full plan and the interview carries on as usual. A build that outgrows those limits stops and suggests /viber:intent. A draft, a roadmap.md or a run on its own branch never takes it, and neither does a fix of code-audit findings or pull request review threads: that fix never takes the fast path.Przy włączonym planning.fast-path wywiad kieruje zmianę istniejącego kodu na co najwyżej 2 zadania z kodem i 5 w sumie, bez nowego podsystemu, przebudowy ani pojęcia domenowego, na szybką ścieżkę: krótki projekt na czacie, zbudowany w twojej sesji po twoim wyraźnym „tak”, sprawdzony przez test-runner, bez pliku planu i bez katalogu przebiegu. Poprawka daje poprawiony projekt; poproś o pełny plan, a wywiad toczy się dalej jak zwykle. Build, który przerośnie te limity, zatrzymuje się i proponuje /viber:intent. Nigdy nie idzie nią szkic, roadmap.md ani przebieg na własnej gałęzi, a poprawka ustaleń audytu kodu lub wątków recenzji pull requesta nigdy nie idzie szybką ścieżką.

Fix a bugNapraw błąd#

Start here when something works wrong and you want it fixed through a plan. The cause is proven before any fix is written.

Zacznij tutaj, gdy coś działa źle i chcesz to naprawić przez plan. Przyczyna zostaje udowodniona, zanim powstanie jakakolwiek poprawka.

  1. You typeWpisujesz

    /viber:fixer saving a draft with an empty title returns 500

    /viber:fixer zapis szkicu z pustym tytułem zwraca 500

  2. viber doesviber robi

    fixer follows the code from its entry point, step by step, to the first place where the actual value differs from the expected one. It writes a test that reproduces that divergence, runs it and watches it fail, then hands the diagnosis to planner. It changes no code apart from that test.

    fixer idzie za kodem od punktu wejścia, krok po kroku, do pierwszego miejsca, w którym faktyczna wartość różni się od oczekiwanej. Pisze test odtwarzający tę rozbieżność, uruchamia go i sprawdza, że nie przechodzi, a potem przekazuje diagnozę do planner. Poza tym testem nie zmienia kodu.

  3. What is leftCo zostaje

    A failing test in your suite and a plan to approve. Once the plan is built, the test passes and the fix is committed task by task.

    Nieprzechodzący test w twoich testach i plan do zatwierdzenia. Po zbudowaniu planu test przechodzi, a poprawka jest zacommitowana zadanie po zadaniu.

Several possible fixes, or a bug that resists a testKilka możliwych poprawek albo błąd, którego nie da się łatwo odtworzyć
  • When more than one fix is defensible, it asks you which one before it hands off.Gdy da się obronić więcej niż jedną poprawkę, przed przekazaniem pyta cię, którą wybrać.
  • When a reproduction is really impossible (a hard race, a rendering artifact, third party state it cannot reach), it stops and asks your explicit permission to hand off without the test. A bug that is only hard to test still gets its test.Gdy błędu naprawdę nie da się odtworzyć (trudny wyścig, artefakt renderowania, stan zewnętrznej usługi poza zasięgiem), zatrzymuje się i prosi cię o wyraźną zgodę na przekazanie bez testu. Błąd, który jest tylko trudny do przetestowania, i tak dostaje test.
  • With github.issues on, /viber:fixer #42 reads the issue as the bug report. When the issue cannot be read, it stops before tracing anything.Przy włączonym github.issues /viber:fixer #42 czyta issue jako opis błędu. Gdy issue nie da się odczytać, zatrzymuje się, zanim zacznie cokolwiek śledzić.

Start from a GitHub issueZacznij od issue na GitHubie#

Set github.issues to true in .claude/viber.yml first (the template ships it off) and install the GitHub CLI (gh). With the switch off, /viber:triage assesses pasted issue text only.

Najpierw ustaw github.issues na true w .claude/viber.yml (szablon ma go wyłączonego) i zainstaluj GitHub CLI (gh). Przy wyłączonym przełączniku /viber:triage ocenia tylko wklejony tekst issue.

  1. You typeWpisujesz

    /viber:triage #42

How viber worksJak działa viber#

Plan before codeNajpierw plan, potem kod#

While viber is installed, Claude writes or edits no code before you approve a plan. The plan names the acceptance criteria, the files it touches and the tasks, and a review agent checks it against your code before you see it, so a wrong assumption shows up before any code depends on it.

Dopóki viber jest zainstalowany, Claude nie pisze ani nie zmienia kodu, zanim nie zatwierdzisz planu. Plan podaje kryteria akceptacji, pliki, których dotyczy, i zadania, a agent recenzujący sprawdza go na twoim kodzie, zanim go zobaczysz. Błędne założenie wychodzi więc na jaw, zanim oprze się na nim jakikolwiek kod.

For a change you want made right away, say so: an explicit request for a direct change skips the plan. The one piece of code allowed before a plan is the failing test fixer writes to prove a bug.

Jeśli chcesz zmianę od razu, powiedz to wprost: wyraźna prośba o bezpośrednią zmianę pomija plan. Jedyny kod dopuszczalny przed planem to nieprzechodzący test, którym fixer udowadnia błąd.

The plan-mode gateBramka trybu planowania#

The plan gate is a hook that holds Claude inside plan mode until a review agent has passed the latest version of the plan. A plan the planner wrote goes to planner-review; a planner plan past 12 tasks goes to planner-spec-review, planner-graph-review and planner-task-review at once, and plan mode ends only when all of them pass. A plan written in plain plan mode goes to plain-plan-review, as long as planning.plain-plan-review is on, and may name at most 8 repository files: past that, the gate points to /viber:intent.

Bramka planu to hook, który trzyma Claude w trybie planowania, dopóki agent recenzujący nie zaakceptuje najnowszej wersji planu. Plan napisany przez planistę trafia do planner-review; plan planisty powyżej 12 zadań trafia do planner-spec-review, planner-graph-review i planner-task-review jednocześnie, a tryb planowania kończy się dopiero wtedy, gdy przejdą wszyscy. Plan napisany w zwykłym trybie planowania trafia do plain-plan-review, o ile włączony jest przełącznik planning.plain-plan-review, i może wskazywać najwyżej 8 plików repozytorium: powyżej bramka odsyła do /viber:intent.

Any change to the plan after the pass voids it, so the plan is reviewed again before plan mode can end. When the gate blocks, Claude gets the next step in words (run the review, fix its findings, or grant a permission the reviewer was refused), and the message says it comes from the gate and is no error.

Każda zmiana planu po akceptacji ją unieważnia, więc przed wyjściem z trybu planowania plan przechodzi recenzję jeszcze raz. Kiedy bramka blokuje wyjście, Claude dostaje opis następnego kroku (uruchom recenzję, popraw uwagi albo nadaj uprawnienie, którego odmówiono recenzentowi), a komunikat mówi, że pochodzi od bramki i nie jest błędem.

The run directory and its archiveKatalog przebiegu i archiwum#

A build copies the approved plan into its own directory, docs/_specs/<stamp>_<slug>/, and cuts it there into spec.md, the specification, and one file per task under tasks/. status.md records which tasks are done or skipped, and work/ holds the agents' notes and reports.

Build kopiuje zatwierdzony plan do własnego katalogu, docs/_specs/<stamp>_<slug>/, i tam dzieli go na spec.md, czyli specyfikację, oraz osobny plik dla każdego zadania w tasks/. status.md zapisuje, które zadania są ukończone lub pominięte, a w work/ leżą notatki i raporty agentów.

A plan of one part of a split request also gets roadmap.md: the parts and the decisions settled for the later ones. A plan built from files under .temp/, such as a mockup or a code-auditor findings.md, lists them as attachments: the plan's copies land in attachments/, spec.md lists them under ## Attachments, and only a task that needs one names it. When the build rules where it would otherwise have asked you, it also writes rulings.md: one line per ruling, with its reason and what it costs if wrong. A build that ruled nothing has no such file.

Plan jednej części dzielonej prośby dostaje też roadmap.md: listę części i decyzje podjęte dla późniejszych. Plan zbudowany na plikach z .temp/, takich jak makieta albo findings.md z code-auditor, wymienia je jako załączniki: kopie planu trafiają do attachments/, spec.md wypisuje je pod ## Attachments, a wskazuje je tylko zadanie, które ich potrzebuje. Gdy build rozstrzyga tam, gdzie inaczej by cię zapytał, zapisuje też rulings.md: jedna linia na rozstrzygnięcie, z uzasadnieniem i kosztem pomyłki. Build, który niczego nie rozstrzygał, nie ma tego pliku.

The directory is committed together with every task, which is why a build resumes in a new session or on another machine.

Katalog jest commitowany razem z każdym zadaniem, dlatego build da się wznowić w nowej sesji albo na innym komputerze.

With build.cleanup on, the build ends by moving the run to docs/specs/<stamp>_<slug>/ in one commit. The archive keeps the specification and the QA documents and drops plan.md, status.md, tasks/ and work/, which git history still holds; roadmap.md, attachments/, rulings.md and the build summary outcome.md stay in the archive with them. A run with a task neither done nor skipped is never archived. directories renames both directories.

Przy włączonym build.cleanup build kończy się przeniesieniem przebiegu do docs/specs/<stamp>_<slug>/ w jednym commicie. Archiwum zachowuje specyfikację i dokumenty QA, a usuwa plan.md, status.md, tasks/ i work/, które nadal są w historii gita; roadmap.md, attachments/, rulings.md i podsumowanie buildu outcome.md zostają w archiwum razem z nimi. Przebieg z zadaniem ani ukończonym, ani pominiętym nigdy nie trafia do archiwum. Nazwy obu katalogów zmienisz kluczem directories.

Tasks, review and one commit eachZadania, recenzja i osobny commit#

A task file is the whole input of its coder: the goal, the files it may touch, how to verify the work and its numbered definition of done. The coder never sees the rest of the plan. Tasks whose dependencies are done run side by side, and a task marked exclusive runs alone.

Plik zadania to cały materiał wejściowy jego wykonawcy: cel, pliki, które wolno mu zmienić, sposób weryfikacji i ponumerowana definicja ukończenia. Reszty planu wykonawca nie widzi. Zadania, których zależności są już ukończone, idą równolegle, a zadanie oznaczone jako wyłączne działa samo.

task-coder implements the task and proves it green, test first when the task says TDD: required. task-reviewer then checks it against its definition of done, within the task's 5 attempts. Review is skipped only for a task on the sonnet tier whose verification runs your build or tests; a task verified by a text check is always reviewed, and so is every TDD: required task.

task-coder realizuje zadanie i dowodzi, że testy przechodzą, zaczynając od testu, gdy zadanie ma TDD: required. Potem task-reviewer sprawdza je względem definicji ukończenia, w ramach 5 prób zadania. Recenzję pomija tylko zadanie na poziomie sonnet, którego weryfikacja uruchamia budowanie albo testy projektu; zadanie weryfikowane sprawdzeniem tekstu zawsze przechodzi recenzję, podobnie jak każde zadanie z TDD: required.

A TDD: required task is sealed three ways. Its coder shows the failing run of its new tests before the first production edit, or the attempt fails. With build.red-check on, the build reruns those tests in a separate checkout without the production change, and tests that pass there send the task back. Its reviewer checks that the tests that failed are the task's new ones.

Zadanie z TDD: required ma trzy zabezpieczenia. Jego wykonawca pokazuje nieudany przebieg nowych testów przed pierwszą zmianą kodu produkcyjnego, inaczej próba przepada. Przy włączonym build.red-check build uruchamia te testy ponownie w osobnej kopii roboczej bez zmiany produkcyjnej, a testy, które tam przejdą, odsyłają zadanie do wykonawcy. Recenzent sprawdza, że nie przeszły właśnie nowe testy zadania.

A task that passes gets its own commit, titled T3 - <task title>. Only viber's scripts commit, never an agent.

Zadanie, które przejdzie, dostaje własny commit z tytułem T3 - <tytuł zadania>. Commitują wyłącznie skrypty viber, nigdy agent.

After the last task test-runner runs your fast command, then the integration tests the build's change reaches, found through your layer markers. Without a fast command or a layer marker convention in your project's instructions it runs every layer but end-to-end. It runs up to six times, with a repair round between one failed run and the next, before the arbiter rules on the failing tests.

Po ostatnim zadaniu test-runner uruchamia twoją szybką komendę testów, a potem testy integracyjne, których dotyka zmiana builda, wskazane przez znaczniki warstw. Gdy instrukcje projektu nie podają szybkiej komendy albo konwencji znaczników warstw, uruchamia każdą warstwę poza end-to-end. Uruchamia je najwyżej sześć razy, z rundą poprawek między jednym nieudanym uruchomieniem a kolejnym, zanim arbiter rozstrzygnie, co zrobić z niepasującymi testami.

With build.baseline-tests set to fast or full, it also makes a baseline run: the tests once before the first task (fast the unit and component tests, full every layer but end-to-end), recording what already fails; when something does, the arbiter rules to continue and the ruling is recorded. From then on only the failures the build caused count as repair work.

Gdy build.baseline-tests ma wartość fast lub full, wykonuje też przebieg bazowy: raz przed pierwszym zadaniem uruchamia testy (fast testy jednostkowe i komponentowe, full każdą warstwę poza end-to-end) i zapisuje, co już nie przechodzi; gdy coś nie przechodzi, arbiter orzeka kontynuację, a orzeczenie zostaje zapisane. Od tej chwili do naprawy idą tylko błędy spowodowane przez build.

The model rangeZakres modeli#

The plan settles every design choice of a task, so most tasks run on sonnet. The build gives every task a tier: haiku for mechanical work such as config, a rename or docs, opus only for a task the plan marks hard because it cannot settle its design in advance (concurrency, security, an algorithm spanning modules, a migration of live data), sonnet for everything else.

Plan rozstrzyga każdy wybór projektowy zadania, więc większość zadań działa na sonnet. Build dobiera każdemu zadaniu poziom modelu: haiku do prac mechanicznych, takich jak konfiguracja, zmiana nazwy czy dokumentacja, opus tylko do zadania, które plan oznacza jako trudne, bo nie da się z góry rozstrzygnąć jego projektu (współbieżność, bezpieczeństwo, algorytm obejmujący kilka modułów, migracja danych w użyciu), sonnet do całej reszty.

A reviewer runs on the task's tier, with haiku raised to sonnet, and on opus for a task whose contract three or more other tasks use. A retry after a failed attempt goes one tier up. tiers keeps all of it between min and max, haiku and opus by default, and fable runs only when max names it. Planning runs on your session's own model.

Recenzent działa na poziomie zadania, przy czym haiku zostaje podniesione do sonnet, a zadanie, którego kontraktu używają co najmniej trzy inne zadania, recenzuje opus. Ponowienie po nieudanej próbie idzie poziom wyżej. Klucz tiers trzyma to wszystko w przedziale od min do max, domyślnie od haiku do opus, a fable działa tylko wtedy, gdy wskazuje go max. Planowanie działa na modelu twojej sesji.

What the build close writesCo zapisuje zamknięcie buildu#

Once the fast tests and the change's integration tests pass, or the arbiter accepts their failure, the build runs the close parts your switches turn on:

Gdy szybkie testy i testy integracyjne zmiany przejdą albo arbiter zaakceptuje ich porażkę, build uruchamia te części zamknięcia, które włączają twoje przełączniki:

  • build.memory: memory-writer folds what the build taught into your CLAUDE.md nodes below the root, within their size budget and in the fixed template, and only suggests changes to the root, which stays yours; the root cause of a fixed defect goes in as the first trap of the run;build.memory: memory-writer przenosi to, czego nauczył build, do twoich węzłów CLAUDE.md poniżej głównego pliku, w granicach ich limitu rozmiaru i w stałym szablonie, a zmiany w głównym pliku tylko sugeruje, bo zostaje twój; przyczynę źródłową naprawionego błędu zapisuje jako pierwszą pułapkę przebiegu;
  • build.rules: rules-writer folds the conventions the build confirmed into .claude/rules/, in the same commit as the memory update; it never compacts, splits or moves your existing rule files, and points to /viber:rules when one is over budget;build.rules: rules-writer przenosi konwencje potwierdzone przez build do .claude/rules/, w tym samym commicie co aktualizacja pamięci; nigdy nie kompresuje, nie dzieli ani nie przenosi twoich istniejących plików reguł, a gdy któryś przekracza limit, wskazuje /viber:rules;
  • build.qa: qa-writer writes into the run directory, in a commit of their own, qa.md, the scenarios a person performs, when the UI changed, and qa.e2e.md, the handoff /viber:e2e reads, when the UI or the endpoints changed; a change with neither writes nothing. The build then posts qa.md as a comment on the run's issue, or on the pull request of the run branch when the run has no issue, once per run, each scenario opening on a checkbox the tester ticks there once it is performed;build.qa: qa-writer zapisuje w katalogu przebiegu, we własnym commicie, qa.md, scenariusze do wykonania przez człowieka, gdy zmienił się interfejs użytkownika, oraz qa.e2e.md, plik przekazania dla /viber:e2e, gdy zmienił się interfejs albo endpointy; zmiana bez żadnego z nich nie zapisuje nic. Potem build publikuje qa.md jako komentarz pod issue przebiegu, a gdy przebieg nie ma issue, pod pull requestem jego gałęzi, raz na przebieg, a każdy scenariusz zaczyna się od checkboxa, który tester zaznacza tam po jego wykonaniu;
  • build.extensions: each agent of your own .claude/agents/ that the map has an entry for runs after the writers above and before the archive, and the files it writes land in a commit of their own. A failed extension is named in the summary and never stops the archive, and an aborted build skips this part. /viber:extension creates and registers one;build.extensions: każdy agent z twojego katalogu .claude/agents/, który ma wpis w mapie, działa po powyższych writerach i przed archiwizacją, a pliki, które zapisuje, trafiają do osobnego commita. Nieudane rozszerzenie jest wymienione w podsumowaniu i nigdy nie wstrzymuje archiwizacji, a przerwany build pomija tę część. /viber:extension tworzy i rejestruje takiego agenta;
  • build.cleanup: closeout notes on the specification what the build delivered beyond it, records every file the build left uncommitted with its reason, commits those left without a deliberate reason, then archives the run. An aborted build skips this part.build.cleanup: closeout odnotowuje w specyfikacji to, co build dostarczył ponad nią, zapisuje każdy plik, który build zostawił niezacommitowany, z powodem, commituje te zostawione bez celowego powodu, a potem archiwizuje przebieg. Przerwany build pomija tę część.

The build composes a short summary: the tasks committed, the review rounds spent, the test verdict, the time it took, what memory, rules and QA recorded, the archive path when the run is archived, and anything left for you, such as an unreviewed task or changed files no task claimed. When the run is archived, the screen shows only a short result (the tasks committed, the test verdict and the time, then the path of outcome.md) and one sentence saying whether outcome.md records a problem, plus the /viber:intent command for the next roadmap part when one is left, and the full summary sits in outcome.md in the archive. When nothing is archived, the full summary prints on screen.

Build składa krótkie podsumowanie: zacommitowane zadania, zużyte rundy recenzji, wynik testów, czas trwania, to, co zapisały pamięć, reguły i QA, ścieżka archiwum, gdy przebieg trafia do archiwum, oraz wszystko, co zostaje dla ciebie, na przykład zadanie bez recenzji albo zmienione pliki, do których nie przyznało się żadne zadanie. Gdy przebieg trafia do archiwum, ekran pokazuje tylko krótki wynik (zacommitowane zadania, wynik testów i czas, potem ścieżkę outcome.md) i jedno zdanie, czy outcome.md zapisuje problem, a gdy zostaje kolejna część roadmapy, także polecenie /viber:intent, które ją zaczyna; pełne podsumowanie leży w outcome.md w archiwum. Gdy nic nie trafia do archiwum, pełne podsumowanie pojawia się na ekranie.

With build.final-review on, the summary lists each finding of the final review with what was wrong and what the fix changed, followed by any findings left for you, the owner. After it comes the list of the build's rulings, each with its reason and its cost if wrong, the same lines as in rulings.md.

Gdy build.final-review jest włączony, podsumowanie wymienia każdą uwagę recenzji końcowej wraz z tym, co było nie tak i co zmieniła poprawka, a po nich uwagi zostawione dla ciebie, właściciela. Po nim idzie lista rozstrzygnięć buildu, każde z uzasadnieniem i kosztem pomyłki, te same linie co w rulings.md.

TroubleshootingGdy viber zawodzi#

Why does the build stop on my plan without building anything?Dlaczego build zatrzymuje się na moim planie i nic nie buduje?

The plan is a draft: it has no tasks yet, so there is nothing to build. The build prints its path and stops. To continue it, point /viber:intent at that draft, for example /viber:intent docs/_specs/<stamp>_<slug>/plan.md. Once a round adds the tasks, the build takes it.

Plan jest szkicem: nie ma jeszcze zadań, więc nie ma czego budować. Build podaje jego ścieżkę i kończy pracę. Żeby go kontynuować, wskaż ten szkic w /viber:intent, na przykład /viber:intent docs/_specs/<stamp>_<slug>/plan.md. Gdy kolejna runda dopisze zadania, build go przyjmie.

Why can't Claude leave plan mode?Dlaczego Claude nie może wyjść z trybu planowania?

The plan gate holds it there until a review agent passes the latest version of the plan. Claude gets the next step along with the refusal and normally carries it out on its own: it runs the review, fixes the findings, or has the plan reviewed again after an edit. You step in only when the reviewer was refused a tool call: allow that call when Claude asks. A plan past 12 tasks needs every reviewer of its review set to pass, and a plain plan-mode plan that names more than 8 repository files is refused with a pointer to /viber:intent.

Trzyma go tam bramka planu, dopóki agent recenzujący nie zaakceptuje najnowszej wersji planu. Razem z odmową Claude dostaje następny krok i zwykle wykonuje go sam: uruchamia recenzję, poprawia uwagi albo po zmianie zleca recenzję jeszcze raz. Ty wkraczasz tylko wtedy, gdy recenzentowi odmówiono wywołania narzędzia: zezwól na nie, gdy Claude poprosi. Plan powyżej 12 zadań wymaga akceptacji każdego recenzenta swojego zestawu, a plan ze zwykłego trybu planowania, który wskazuje więcej niż 8 plików repozytorium, jest odrzucany ze wskazaniem na /viber:intent.

Why does Claude write a plan instead of changing the code?Dlaczego Claude pisze plan, zamiast zmienić kod?

viber asks for an approved plan before any code (see Plan before code). Say you want the change made directly, without a plan, and Claude makes it.

viber wymaga zatwierdzonego planu przed jakimkolwiek kodem (zobacz Najpierw plan, potem kod). Powiedz, że chcesz zmianę od razu, bez planu, a Claude ją wprowadzi.

Why does Claude suggest the interview when I ask for a plan?Dlaczego Claude proponuje wywiad, gdy proszę o plan?

The planner starts only from a confirmed /viber:intent interview or a /viber:fixer diagnosis, so any other request gets that suggestion, however clear it is. Agree to the interview, or ask for Claude Code's own plan mode for a small change. A small change to existing code needs no plan at all on the interview's fast path: a short design you approve in chat.

Planista startuje wyłącznie od potwierdzonego wywiadu /viber:intent albo diagnozy /viber:fixer, więc każda inna prośba, nawet bardzo jasna, kończy się taką propozycją. Zgódź się na wywiad albo przy małej zmianie poproś o zwykły tryb planowania Claude Code. Mała zmiana istniejącego kodu na szybkiej ścieżce wywiadu w ogóle nie potrzebuje planu: wystarczy krótki projekt, który zatwierdzasz na czacie.

Why does the build stop at once, saying the run branch could not be set?Dlaczego build od razu się zatrzymuje z informacją, że nie da się ustawić gałęzi przebiegu?

With branching.mode set to allowed or required, the run works on its own branch, and the build lands nothing until it is on it. The message names the reason, for example uncommitted changes while the branch points at another commit. Commit or stash them, then ask for the build again.

Gdy branching.mode ma wartość allowed albo required, przebieg pracuje na własnej gałęzi i build niczego nie zaczyna, dopóki się na niej nie znajdzie. Komunikat podaje powód, na przykład niezacommitowane zmiany, gdy gałąź wskazuje inny commit. Zacommituj je albo odłóż przez stash i poproś o build jeszcze raz.

Under required, a run branch that is the base of any work entry is refused as well: a required run never commits onto an entry's base, so plan the change again on its own branch.

Przy required odrzucana jest też gałąź przebiegu będąca bazą któregokolwiek wpisu work: przebieg required nigdy nie commituje na bazę wpisu, więc zaplanuj zmianę jeszcze raz na jej własnej gałęzi.

What happens when a task keeps failing?Co się dzieje, gdy zadanie ciągle się nie udaje?

Each failure is retried without asking, one tier up, up to 5 attempts. From the second, when the coder proposed a way out, the arbiter picks one of the coder's proposals, the build records it as a decision and runs a fresh coder.

Każda porażka jest ponawiana bez pytania, poziom modelu wyżej, do 5 prób. Od drugiej, gdy wykonawca zaproponował wyjście, arbiter wybiera jedną z propozycji wykonawcy, build zapisuje ją jako decyzję i uruchamia nowego wykonawcę.

After the fifth failed attempt the task is held, and a repair pass runs before the final review, at the highest tier, a deferred path no task claims getting one too. When the repair pass fails as well, the arbiter rules to skip the task or, after a failed review, to accept it. Skipping a task also skips every task that depends on it and leaves its half-finished files uncommitted; accepting commits it marked unreviewed. Every ruling goes to rulings.md with its reason and its cost if wrong. A stalled task never ends on a question.

Po piątej nieudanej próbie zadanie czeka, a przed recenzją końcową, na najwyższym poziomie modelu, idzie naprawa zadania; dostaje ją też odłożona ścieżka, której nie przyznaje się żadne zadanie. Gdy i naprawa zawiedzie, arbiter orzeka pominięcie zadania albo, po odrzuconej recenzji, jego zaakceptowanie. Pominięcie zadania pomija też każde zadanie od niego zależne, a jego niedokończone pliki zostają niezacommitowane; zaakceptowanie commituje je z oznaczeniem, że nie przeszło recenzji. Każde orzeczenie trafia do rulings.md z uzasadnieniem i kosztem pomyłki. Utknięte zadanie nigdy nie kończy się pytaniem.

A question says an agent's tool call was refused. What now?Pytanie mówi, że agentowi odmówiono wywołania narzędzia. Co teraz?

Your permissions blocked a call the agent needed, and the question names it. Allow that call, then answer permission added and retry. /viber:setup puts viber's recommended permissions into .claude/settings.json, and running it again after a plugin update adds the new ones.

Twoje uprawnienia zablokowały wywołanie, którego agent potrzebował, a pytanie je podaje. Zezwól na nie i odpowiedz permission added and retry. /viber:setup wpisuje zalecane uprawnienia viber do .claude/settings.json, a uruchomiony ponownie po aktualizacji wtyczki dopisuje nowe.

Why does the build say a task produced no changes to commit?Dlaczego build mówi, że zadanie nie dało żadnych zmian do zacommitowania?

The task's files show no change. If its work already went into another commit, pick the first option the build offers, that the task is already committed, and name that commit: the task is recorded as done against it. Otherwise retry, skip or abort.

Pliki zadania nie mają żadnych zmian. Jeśli jego praca trafiła już do innego commita, wybierz pierwszą opcję, którą podaje build, czyli że zadanie jest już zacommitowane, i wskaż ten commit: zadanie zostanie w nim zapisane jako ukończone. W przeciwnym razie ponów, pomiń albo przerwij.

What if the final test run fails at the end of a build?Co, jeśli na końcu buildu końcowe uruchomienie testów nie przechodzi?

The final run, the fast tests plus the integration tests the change reaches, runs at most six times. After each failed run but the last, a repair coder fixes what the test report names and the tests run again. After the sixth failed run the arbiter rules to accept: the close goes on, the summary names the failing run and rulings.md records the ruling with its reason and its cost if wrong.

Końcowe uruchomienie, czyli szybkie testy i testy integracyjne, których dotyka zmiana, odbywa się najwyżej sześć razy. Po każdym nieudanym uruchomieniu poza ostatnim wykonawca poprawek naprawia to, co wskazuje raport z testów, i testy uruchamiają się ponownie. Po szóstym nieudanym uruchomieniu arbiter orzeka zaakceptowanie: zamknięcie idzie dalej, podsumowanie wymienia nieudane uruchomienie, a rulings.md zapisuje orzeczenie z uzasadnieniem i kosztem pomyłki.

Why was my run not archived?Dlaczego mój przebieg nie trafił do archiwum?

The archive refuses a run with a task neither done nor skipped, and a destination that already exists, while an aborted build skips the archive altogether. The final summary names the reason. The run stays in docs/_specs/; resume the build, and once its tasks are settled the close archives it.

Archiwum odrzuca przebieg z zadaniem ani ukończonym, ani pominiętym, a także taki, którego katalog docelowy już istnieje, a przerwany build w ogóle pomija archiwizację. Powód podaje podsumowanie końcowe. Przebieg zostaje w docs/_specs/; wznów build, a gdy jego zadania zostaną rozliczone, zamknięcie go zarchiwizuje.

Where did plan.md and the task files go?Gdzie się podziały plan.md i pliki zadań?

With build.cleanup on, the archive keeps the specification, the QA documents, roadmap.md, attachments/, rulings.md and outcome.md and drops the plan, status.md, tasks/ and work/. Git still has them: git log -- docs/_specs/<stamp>_<slug>/plan.md lists the commits that touched the plan.

Przy włączonym build.cleanup archiwum zachowuje specyfikację, dokumenty QA, roadmap.md, attachments/, rulings.md i outcome.md, a usuwa plan, status.md, tasks/ i work/. Git nadal je ma: git log -- docs/_specs/<stamp>_<slug>/plan.md wypisuje commity, które zmieniały plan.

Why does /viber:e2e say the run carries no handoff file?Dlaczego /viber:e2e mówi, że przebieg nie ma pliku przekazania?

That build wrote no qa.e2e.md, for one of two reasons. It ran with build.qa off: turn build.qa on before the next build. Or its change touched neither the UI nor the endpoints, and then there is nothing for end-to-end tests to cover. When the handoff belongs to another run, name that run: /viber:e2e docs/specs/<run>.

Ten build nie zapisał qa.e2e.md z jednego z dwóch powodów. Działał z wyłączonym build.qa: włącz build.qa przed następnym buildem. Albo jego zmiana nie dotknęła ani interfejsu użytkownika, ani endpointów, i wtedy testy end-to-end nie mają czego sprawdzać. Jeśli plik przekazania należy do innego przebiegu, wskaż ten przebieg: /viber:e2e docs/specs/<run>.

Why does /viber:triage ask for the issue text when I give it a number?Dlaczego /viber:triage prosi o tekst issue, gdy podaję jego numer?

github.issues is off, and then viber never reads GitHub. Paste the issue text, or set github.issues: true and install gh.

Przełącznik github.issues jest wyłączony, a wtedy viber nie czyta GitHuba. Wklej tekst issue albo ustaw github.issues: true i zainstaluj gh.

Why does a reset of /viber:memory or /viber:rules refuse to run?Dlaczego reset w /viber:memory albo /viber:rules odmawia działania?

A file on its list holds uncommitted work, which a reset would delete. Nothing was deleted. Commit or discard that work and run the command again.

Plik z jego listy ma niezacommitowane zmiany, które reset by usunął. Nic nie zostało usunięte. Zacommituj te zmiany albo je porzuć i uruchom polecenie ponownie.

Why did /viber:handoff write nothing?Dlaczego /viber:handoff niczego nie zapisał?

A file already exists at that path, and handoff never overwrites one. Run it again with another path, for example /viber:handoff notes/csv-export-2.md.

Pod tą ścieżką już jest plik, a handoff nigdy nie nadpisuje plików. Uruchom go ponownie z inną ścieżką, na przykład /viber:handoff notes/eksport-csv-2.md.

Why does /viber:commit answer Nothing to commit?Dlaczego /viber:commit odpowiada Nothing to commit?

Your working tree has no change to commit, or none under the paths you named.

W drzewie roboczym nie ma zmian do zacommitowania albo nie ma ich pod wskazanymi ścieżkami.

/viber:talk

branching groupgrupa

mode off
off stays on the branch the run started on. allowed lets the run get its own branch, or none if you choose. required always gives the run its own branch and never commits onto the base of any work entry: building on one, or on a detached HEAD, is not offered. Under both, the interview or diagnosis settles the work entry when it starts, before reading any code, and when you are not on that entry's base the interview offers four answers: switch there, stay for now (nothing moves and the run branch is still cut from the base when the plan lands), build on the current branch (no run branch is made and commits land on it) or abort. The diagnosis offers the same without stay, since its reproduction test stays uncommitted. The next part of a roadmap, on a branch that is no entry's base, builds on it without asking. Only building on the current branch pins it: the planner takes the branch from that choice.off zostawia przebieg na gałęzi, na której się zaczął. allowed pozwala przebiegowi dostać własną gałąź albo, jeśli tak wybierzesz, żadnej. required zawsze daje przebiegowi własną gałąź i nigdy nie commituje na bazę żadnego wpisu work: budowanie na takiej bazie albo na odłączonym HEAD nie jest proponowane. W obu przypadkach wywiad albo diagnoza ustala wpis work na samym początku, zanim przeczyta jakikolwiek kod, a gdy nie jesteś na bazie tego wpisu, wywiad proponuje cztery odpowiedzi: przełączenie się na nią, pozostanie na razie (nic się nie przesuwa, a gałąź przebiegu i tak jest wycinana z bazy, gdy plan trafia do repozytorium), budowanie na bieżącej gałęzi (gałąź przebiegu nie powstaje, a commity trafiają na bieżącą) albo przerwanie. Diagnoza proponuje to samo bez pozostania, bo jej test reprodukujący zostaje niezacommitowany. Kolejna część roadmapy na gałęzi, która nie jest bazą żadnego wpisu, buduje na niej bez pytania. Tylko budowanie na bieżącej gałęzi ją przypina: planista bierze gałąź z tego wyboru.
