# viber/scripts - the plugin-level bundled scripts

This directory holds the scripts more than one viber skill or agent calls: the config parser, the run lifecycle, the switch fragment selector, the skill part printer and the GitHub and browser wrappers. A script of one skill lives under that skill's `scripts/`, the hook scripts under `hooks/scripts/`.

## Terms

- Run scripts: the four bash scripts of the run lifecycle, `plan-path.sh`, `plan-index.sh`, `commit-task.sh` and `archive-run.sh`, all `set -euo pipefail`, each refusal a distinct exit code.
- GitHub wrappers: the `#!/bin/sh` scripts `issue-facts.sh`, `issue-templates.sh`, `issue-create.sh`, `post-comment.sh`, `pr-facts.sh`, `pr-create.sh`, `pr-threads.sh`, `pr-reply.sh`, `qa-comment.sh`, `artifact-create.sh` and `gh-read.sh`. Each prints its fixed `KEY=value` block only after `gh` succeeded and its output parsed (self-verifying), else one `ERROR <script>: ...` line on stderr; the bash scripts report on stderr as `error: ...` (the plan defects of `plan-index.sh` as `FIX:` or `SPLIT:` lines). `issue-templates.sh`, `qa-comment.sh`, `pr-reply.sh` and `pr-facts.sh` print a `SAY=` sentence after each skip or stop `REASON=`, which the caller states and never rewords. The wrappers carry their other directives as `KEY=` lines (`RUN=`, `ASK=`, `RERUN=`); `NEXT:`, `RUN:`, `ASK:` and `STOP:` lines belong to the bash scripts and `arg-kind.sh`.

## Relationships

- Callers: `config.sh` is preloaded by `implementor`, `planner`, `e2e` and `intent` (`--questions`) and run by `skills/extension/scripts/extension.sh` and `hooks/scripts/plan-gate.sh`; `run-summary.sh` by `implementor` alone; `run-changes.sh` and `run-suite.sh` by `test-runner` alone; `switch-text.sh` by `implementor`, `planner`, `intent`, `fixer` and `prototype`; `skill-part.sh` by `implementor` (its `close` part) and `intent` (its `done` part); `plan-path.sh` by `planner`, `implementor`, `intent` and `fixer` (`--start`/`--checkout`) and `e2e` (no argument, the latest run); `plan-index.sh` by `planner` (validate, `--input`) and by `skills/planner/scripts/review-round.sh` (its `start`), `implementor` (`--split`), `task-step.sh` (the index, `--dispatch`), `task-reviewer` (`--extra`, through its `scope` line), `final-reviewer` (`--slice`, through its `scope` line) and `implementor` (`--final-review`, the index blocks); `commit-task.sh` by `implementor` (`--drop` and `--repair` included), `e2e` (`--e2e`) and `closeout` (`--leftovers`); `archive-run.sh` by the `closeout` agent alone; `task-step.sh` by `implementor` alone; `red-check.sh` by `task-step.sh` alone; `run-failures.sh` by `implementor`, `run-failures.sh --lessons` also by `task-step.sh`.
- GitHub callers: `issue-facts.sh` by `intent`, `fixer`, `prototype`; `issue-templates.sh` and `issue-create.sh` by `issue-create`, `intent`, `fixer`; `post-comment.sh` by `intent`, `prototype`; `artifact-create.sh` by `attach` and `prototype`; `pr-facts.sh` and `pr-create.sh` by `pr-create`; `pr-threads.sh` by `pr-feedback` and `pr-feedback-reply`; `pr-reply.sh` by `pr-feedback-reply`; `qa-comment.sh` by `pr-create` and the `implementor` close (`qa.true.md`); `gh-read.sh` by `talk`; `open-page.sh` by `setup`, `help`, `prototype`; `check-playwright.sh` by `e2e`; `arg-kind.sh issue` by `intent`, `fixer` and `prototype`, `arg-kind.sh pr` by `pr-feedback` and `pr-feedback-reply`; `attach-lines.sh` by `intent` and `fixer`.
- `config.sh`, `switch-text.sh`, `arg-kind.sh`, `attach-lines.sh`, `skill-part.sh`, `run-changes.sh` and `run-failures.sh` are wrappers, each running the `.ts` entry of its name beside it (contract in the entry header, core in `../lib/`); `switch-text.ts` and `run-failures.ts` read the config through the core, never through `config.sh`, and `skill-part.ts` resolves each fragment through the switch-text core, never through `switch-text.sh`.
- Sibling calls: `plan-path.sh` sources `run-branch.sh`; `run-branch.sh` runs `config.sh --branching` and `sh issue-facts.sh`; `gh-read.sh issue` runs `sh issue-facts.sh`; `red-check.sh` runs `plan-index.sh` and `config.sh --red-check`; `task-step.sh` runs `plan-index.sh`, `config.sh`, `run-failures.sh --lessons` and `red-check.sh`, all beside it.

## Contracts

- `run-branch.sh` is a library: sourced by `plan-path.sh`, never invoked, mode 100644 in the index, no `set` line of its own. Its functions return 5 with the reason on stderr and HEAD, index and tree untouched; `plan-path.sh` turns that into its own exit 5 (run branch could not be set).
- `plan-path.sh --start` under `allowed` or `required` prints `branch_report`'s lines unchanged and, after them, the decision `branch_decide` and its `decide_*` helpers build in `run-branch.sh` from `st_*` entry rows and `tl_*` tail values: `next:` (`settled`, `kept`, `ask-entry`, `ask-base`, `errors`, `none`, `abort`), `settled:`, `option:` per answer and `note:`, each `option:` carrying the `run:` command to run and the `settle:` value to settle, which the skill's fragment acts on without a per-answer rule; the `plan-path.sh` header lists the rules. The `<plugin root>` of a printed command comes from `plugin-root.sh` (sourced by every script that prints a plugin path, `plugin_root_of <$0> <levels above the script directory>`): the invoked path as text, backslashes read as `/`, never `pwd`, so `C:\...` and `C:/...` print `C:/...`, `/c/...` prints `/c/...` and a relative one a relative root, and the `${CLAUDE_PLUGIN_ROOT}` form of the `allowed-tools` prefixes survives on Windows. `skill-part.sh` and `switch-text.sh` derive it from the skill directory they are given instead. A flag value beginning with `--` counts as missing (exit 2). `plan-path.sh --branch` likewise ends its report on the planner decision `branch_plan_decide` and its `plan_*` helpers build from `pb_*` entry rows and its `--work`, `--name` and `--entry` flags: `next:` (`write`, `kept` when the frontmatter's recorded `work:` and `branch:` equal an answer or an ask option, `ask`, `ask-entry`, `errors`, `stop`), `work:`, `branch:`, `show:`, `option:` (with `run:` and `settle:`) and `note:`, which the planner's `branching` fragments only act on; a `--start --settled nothing --entry <key>` call gets that entry's base check.
- `plan-path.sh --land` rewrites the landed copy's `source:` line to the copy's own path and adds `planned: <absolute path of the source plan>` right after it, unless the frontmatter already holds one (a frontmatter with no `source:` gets neither): `run-summary.sh` finds the planning transcripts by that path.
- Exit codes of the run scripts are part of their contract, each documented in the header: `plan-path.sh` 2 argv, 3 no plan, 4 copy failed, 5 run branch, 6 unusable `attachments:` map (checked on every `--land` before the branch step); `plan-index.sh` 2 unusable plan or argv, 3 no task blocks, 4 broken task contract (each defect a `FIX:` or `SPLIT:` line); `commit-task.sh` 2 bad arguments, 3 no such task, 4 no change, 5 staging or commit failed; `archive-run.sh` 2 argv outside `docs/<runs>/` or with no run key, 3 destination exists, 4 run unfinished, 5 a git step failed.
- `skill-part.sh <skill dir> <part>` prints `<skill dir>/parts/<part>.md`, resolving only a ```` ```! ```` block whose single body line is the exact `switch-text.sh` call shape (header of `skill-part.ts`) and replacing it, fences included, by what the switch-text core returns for that call, in process; any other block prints as plain text, and no command of a part is run. A fragment is appended as the switch-text core returned it, never expanded twice; the placeholders of every other line are expanded here.
- `config.sh`'s `--branching` report is read by `run-branch.sh` and `pr-facts.sh` only, `--red-check` by `red-check.sh` only, `--specifications` by `rules-map.sh` only (it falls back to `specs`; the run-failures core resolves the same value in process), `--questions` by the `intent` preload only (the default block carries no line for that key, though its `# local:` line names it); every other reader takes the default block.

- `task-step.sh <plan> <subject> <started> <event>` answers each return of a task agent with blocks, each opening on `NEXT:`, `RUN:`, `ASK:` or `STOP:`: the body lines after it are sent verbatim in the dispatch the verb names, and an `add:` field names a line the model copies from the return it holds (`reason`, `repair`). The header defines every event, verb and field. It keeps the task step in `.temp/viber/<id>/state`, discarded when written under another `started:` mark, and the session lessons in `.temp/viber/lessons`; it takes no free text in its arguments and exits 2 with one `error:` line and an empty stdout.

## Commands

- `config.sh`: logic by `tests/viber/config/*.unit.test.ts`, wrapper by `tests/viber/config.critical.test.ts`. `switch-text.sh`, `arg-kind.sh`, `attach-lines.sh`, `skill-part.sh`, `run-changes.sh` and `run-failures.sh`: logic by `tests/viber/lib/<basename>.unit.test.ts`, wrapper by `tests/viber/<basename>.critical.test.ts`. Every other script's test is the legacy pair `tests/viber/<basename>.critical.test.ts` and `tests/viber/<basename>.test.ts` (run only by `legacy.yml`, `tests/CLAUDE.md`), sharing `tests/viber/<basename>-fixture.ts`; `task-step.test.ts` runs about 3 minutes. `run-branch.sh` has no file of its own: `tests/viber/plan-path.test.ts` covers it through `--branch`, `--start`, `--checkout` and `--land`.

## Change together

- The directive format of `task-step.sh`: its header defines it, `skills/implementor/SKILL.md` step 4 acts on each verb, `tests/viber/task-step.test.ts` pins it; the `NEXT:` words `red-check.sh` prints (`review`, `coder-failure`) are read by `task-step.sh`. `skills/memory/scripts/memory-map.sh`, `skills/rules/scripts/rules-map.sh` and `skills/planner/scripts/review-round.sh` answer their script modes in the same `NEXT:`, `ASK:`, `STOP:` blocks.

## Traps

- A fork is what a script costs under Git Bash, tens of milliseconds each, and `config.sh` is called by thirteen scripts: a caller takes the whole block or report in one call, never one call per key; the grammar stays out of the wrapper.
- `skill-part.sh`, `run-summary.sh`, `run-changes.sh`, `run-suite.sh` and `task-step.sh` are invoked bare by `implementor`, so their index mode must stay 100755: the `invocations` lint rule fails on 100644.
- The GitHub wrappers are `#!/bin/sh` and must stay POSIX: CI runs them under every POSIX shell present, and the `script-portability` lint rule flags bash-only syntax in them.
- A failed GitHub call is never retried by its caller: `post-comment.sh` exits 1 when whether the comment landed is unknown, and `pr-create.sh` exits 1 after the push may already have happened (its ERROR line names the pushed branch); `pr-reply.sh` exits 1 when a reply may or may not have landed, and its `--all` reports a failed post as `FAILED=` and posts the next; `artifact-create.sh` retries no create call, and a refusal of one file leaves the others created; the caller reports.
- The `script-portability` rule reads the awk block of a `#!/bin/sh` script (`pr-threads.sh`) as shell: it flags `function NAME` and `((` there, so the block defines no function (`pr-threads.sh`: a sentinel `T` line closes the last thread) and the `--jq` filter avoids `((`.
- `issue-create.sh` never removes a created issue when applying its type or its `--parent` attach fails: the type failure is reported as `TYPE=dropped` or `TYPE=error`, the attach failure as `PARENT=error` with `PARENT_ERROR=`, always with exit 0. `--template <path>` runs `issue-templates.sh` and applies that template's type, labels, assignees and projects; a path no template block holds exits 2 with nothing created.
- `gh-read.sh` is the read-only reader: every `gh api` call in it stays a GET (no `-X`, `-f`, `-F`), which `tests/viber/gh-read.test.ts` asserts; a write belongs in its own wrapper.
- Never edit `task-step.sh` while its test runs: bash reads a script incrementally, so a header edit mid-run shows as a syntax error in the running cases.
