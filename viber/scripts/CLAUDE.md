# viber/scripts - the plugin-level bundled scripts

This directory holds the scripts more than one viber skill or agent calls: the config parser, the run lifecycle with its task step and scheduling, the switch fragment selector, the skill part printer and the GitHub and browser wrappers. A script of one skill lives under that skill's `scripts/`, the hook scripts under `hooks/scripts/`.

## Terms

- Run scripts: the four scripts of the run lifecycle, the bash scripts `plan-path.sh` and `commit-task.sh`, both `set -euo pipefail`, and the wrappers `plan-index.sh` and `archive-run.sh`, each refusal a distinct exit code.
- GitHub wrappers: the `#!/bin/sh` scripts `issue-facts.sh`, `issue-templates.sh`, `issue-create.sh`, `post-comment.sh`, `pr-facts.sh`, `pr-create.sh`, `pr-threads.sh`, `pr-reply.sh`, `qa-comment.sh` and `artifact-create.sh`. Each prints its fixed `KEY=value` block only after `gh` succeeded and its output parsed (self-verifying), else one `ERROR <script>: ...` line on stderr; the bash scripts report on stderr as `error: ...` (the plan defects of `plan-index.sh` as `FIX:` or `SPLIT:` lines). `issue-templates.sh`, `qa-comment.sh`, `pr-reply.sh` and `pr-facts.sh` print a `SAY=` sentence after each skip or stop `REASON=`, which the caller states and never rewords. The wrappers carry their other directives as `KEY=` lines (`RUN=`, `ASK=`, `RERUN=`); `NEXT:`, `RUN:`, `ASK:` and `STOP:` lines belong to the bash scripts and `arg-kind.sh`.

## Relationships

- Callers: `config.sh` is preloaded by `implementor`, `planner`, `e2e` and `intent` (`--questions`) and run by `hooks/scripts/plan-gate.sh`; `run-summary.sh` by `implementor` alone; `run-changes.sh` and `run-suite.sh` by `test-runner` alone; `switch-text.sh` by `implementor`, `planner`, `intent`, `fixer` and `prototype`; `skill-part.sh` by `implementor` (its `close` part) and `intent` (its `done` part); `plan-path.sh` by `planner`, `implementor`, `intent` and `fixer` (`--start`/`--checkout`) and `e2e` (no argument, the latest run); `plan-index.sh` by `implementor` (`--split`, `--final-review`), `task-step.sh` (the index, `--dispatch`), `task-reviewer` (`--extra`, through its `scope` line) and `final-reviewer` (`--slice`, through its `scope` line), and by no planning skill: `skills/planner/scripts/plan-build.sh` runs its fresh-plan and `--input` checks in process (`planDefects` of `lib/plan-index/run.ts`); `commit-task.sh` by `implementor` (`--drop` and `--repair` included), `e2e` (`--e2e`) and `closeout` (`--leftovers`); `archive-run.sh` by the `closeout` agent alone; `task-step.sh` by `implementor` alone; `red-check.sh` and `task-ready.sh` by `task-step.sh` alone; `run-notes.sh` by `commit-task.sh --leftovers` and `run-summary.sh`; `run-failures.sh` by `implementor`, `run-failures.sh --lessons` also by `task-step.sh`.
- GitHub callers: `issue-facts.sh` by `intent`, `fixer`, `prototype`; `issue-templates.sh` and `issue-create.sh` by `issue-create`, `intent`, `fixer`; `post-comment.sh` by `intent`, `prototype`; `artifact-create.sh` by `attach` and `prototype`; `pr-facts.sh` and `pr-create.sh` by `pr-create`; `pr-threads.sh` by `pr-feedback` and `pr-feedback-reply`; `pr-reply.sh` by `pr-feedback-reply`; `qa-comment.sh` by `pr-create` and the `implementor` close (`qa.true.md`); `open-page.sh` by `prototype`; `check-playwright.sh` by `e2e`; `arg-kind.sh issue` by `intent`, `fixer` and `prototype`, `arg-kind.sh pr` by `pr-feedback` and `pr-feedback-reply`; `attach-lines.sh` by `intent` and `fixer`.
- `config.sh`, `switch-text.sh`, `arg-kind.sh`, `attach-lines.sh`, `skill-part.sh`, `run-changes.sh`, `run-failures.sh`, `archive-run.sh`, `plan-index.sh`, `run-notes.sh` and `task-ready.sh` are the eleven wrappers, each running the `.ts` entry of its name beside it (contract in the entry header, core in `../lib/`); `switch-text.ts`, `run-failures.ts` and `plan-index.ts` read the config through the core, never through `config.sh`, and `skill-part.ts` resolves each fragment through the switch-text core, never through `switch-text.sh`.
- Sibling calls: `plan-path.sh` sources `run-branch.sh`; `run-branch.sh` runs `config.sh --branching` and `sh issue-facts.sh`; `red-check.sh` runs `plan-index.sh` and `config.sh --red-check`; `task-step.sh` runs `plan-index.sh`, `config.sh`, `run-failures.sh --lessons`, `red-check.sh` and `task-ready.sh`, `commit-task.sh --leftovers` runs `plan-index.sh` and `run-notes.sh`, and `run-summary.sh` runs `run-notes.sh`, all beside the caller.

## Contracts

- The `<plugin root>` of a printed command comes from `plugin-root.sh` (sourced by every shell script that prints a plugin path, `plugin_root_of <$0> <levels above the script directory>`): the invoked path as text, backslashes read as `/`, never `pwd`, so `C:\...` and `C:/...` print `C:/...`, `/c/...` prints `/c/...` and a relative one a relative root, and the `${CLAUDE_PLUGIN_ROOT}` form of the `allowed-tools` prefixes survives on Windows. `skill-part.sh` and `switch-text.sh` derive it from the skill directory they are given instead, `plan-index.sh` from the absolute path its entry was started by (`C:/...` whichever spelling invoked it).
- Exit codes of the run scripts are part of their contract, each documented in the header: `plan-path.sh` 2 argv, 3 no plan, 4 copy failed, 5 run branch, 6 unusable `attachments:` map (checked on every `--land` before the branch step); `plan-index.sh` 1 a file of `--split` could not be written, 2 unusable plan or argv, 3 no task blocks, 4 broken task contract (each defect a `FIX:` or `SPLIT:` line); `commit-task.sh` 2 bad arguments, 3 no such task, 4 no change, 5 staging or commit failed; `archive-run.sh` 1 a file step failed, 2 argv outside `docs/<runs>/` or with no run key, 3 destination exists, 4 run unfinished, 5 a git step failed; `task-ready.sh` and `run-notes.sh` 2 unusable argv or plan.
- `skill-part.sh <skill dir> <part>` prints `<skill dir>/parts/<part>.md`, resolving only a ```` ```! ```` block whose single body line is the exact `switch-text.sh` call shape (header of `skill-part.ts`) and replacing it, fences included, by what the switch-text core returns for that call, in process; any other block prints as plain text, and no command of a part is run. A fragment is appended as the switch-text core returned it, never expanded twice; the placeholders of every other line are expanded here.
- `config.sh`'s `--branching` report is read by `run-branch.sh` and `pr-facts.sh` only, `--red-check` by `red-check.sh` only, `--specifications` by no script (the run-failures and rules-map cores resolve the same value in process), `--questions` by the `intent` preload only (the default block carries no line for that key, though its `# local:` line names it); every other reader takes the default block.
- `task-step.sh <plan> <subject> <started> <event>` answers each return of a task agent, and the `ready` question of which tasks to start, with blocks opening on `NEXT:`, `RUN:`, `ASK:` or `STOP:`; `implementor` schedules nothing itself. It asks `task-ready.sh` which tasks may run and what a collision of two tasks becomes, and `status.md` carries the outcome: `decision: <id>: sequenced after <other>: both need <path>` for a pair put in sequence, `refused: <id>:<path> ...` for a path a task commit refused.

## Commands

- `config.sh`: logic by `tests/viber/config/*.unit.test.ts`, wrapper by `tests/viber/config.critical.test.ts`. `switch-text.sh`, `arg-kind.sh`, `attach-lines.sh`, `skill-part.sh`, `run-changes.sh`, `run-failures.sh`, `archive-run.sh` and `plan-index.sh`: logic by `tests/viber/lib/<basename>.unit.test.ts` (`plan-index`: a unit file per module under `tests/viber/lib/plan-index/`), wrapper by `tests/viber/<basename>.critical.test.ts`. `run-notes.sh` and `task-ready.sh`: logic by the unit file of their name, no wrapper file of their own (the `commit-task`, `run-summary` and `task-step` pairs run them beside their script). Every other script's test is the legacy pair `tests/viber/<basename>.critical.test.ts` and `tests/viber/<basename>.test.ts` (run only by `legacy.yml`, `tests/CLAUDE.md`), sharing `tests/viber/<basename>-fixture.ts`. `run-branch.sh` has no file of its own: `tests/viber/plan-path.test.ts` covers it through `--branch`, `--start`, `--checkout` and `--land`.

## Change together

- The directive blocks: `task-step.sh` answers in `NEXT:`, `RUN:`, `ASK:` and `STOP:` blocks (`CLAUDE.task-step.md`), `skills/memory/scripts/memory-map.sh` and `skills/rules/scripts/rules-map.sh` answer their script modes in the same `NEXT:`, `ASK:`, `STOP:` blocks, and `skills/planner/scripts/plan-build.sh` in `NEXT:` lines (`dispatch` blocks, `fix`, `judge`, `redispatch`, `exit-plan`) and one `STOP:` line, never an `ASK:`.
- What claims a path for a task (its `Files` and its two extras files, until the task is done or skipped): the ownership check of `commit-task.sh` (`claimants()`, `extras_claimants()`), `lib/task-ready.ts` and `lib/file-guard.ts`.

## Traps

- A fork is what a script costs under Git Bash, tens of milliseconds each, and `config.sh` is run by six scripts (`task-step.sh`, `red-check.sh`, `run-branch.sh`, `pr-facts.sh`, `issue-templates.sh`, `hooks/scripts/plan-gate.sh`): a caller takes the whole block or report in one call, never one call per key; the grammar stays out of the wrapper.
- `skill-part.sh`, `run-summary.sh`, `run-changes.sh`, `run-suite.sh` and `task-step.sh` are invoked bare by `implementor`, so their index mode must stay 100755: the `invocations` lint rule fails on 100644.
- The GitHub wrappers are `#!/bin/sh` and must stay POSIX: CI runs them under every POSIX shell present, and the `script-portability` lint rule flags bash-only syntax in them.
- A failed GitHub call is never retried by its caller: `post-comment.sh` exits 1 when whether the comment landed is unknown, and `pr-create.sh` exits 1 after the push may already have happened (its ERROR line names the pushed branch); `pr-reply.sh` exits 1 when a reply may or may not have landed, and its `--all` reports a failed post as `FAILED=` and posts the next; `artifact-create.sh` retries no create call, and a refusal of one file leaves the others created; the caller reports.
- The `script-portability` rule reads the awk block of a `#!/bin/sh` script (`pr-threads.sh`) as shell: it flags `function NAME` and `((` there, so the block defines no function (`pr-threads.sh`: a sentinel `T` line closes the last thread) and the `--jq` filter avoids `((`.
- `issue-create.sh` never removes a created issue when applying its type or its `--parent` attach fails: the type failure is reported as `TYPE=dropped` or `TYPE=error`, the attach failure as `PARENT=error` with `PARENT_ERROR=`, always with exit 0. `--template <path>` runs `issue-templates.sh` and applies that template's type, labels, assignees and projects; a path no template block holds exits 2 with nothing created.
