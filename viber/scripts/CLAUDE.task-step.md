# viber/scripts - editing the task step, the scheduling and the red check

What `task-step.sh`, `task-ready.sh` and `red-check.sh` keep, read and print between the returns of a task's agents: the step of each task, which tasks may run now, what a collision of two tasks becomes and the control run of a `TDD: required` task. The commit and plan checks stay in `CLAUDE.run-scripts.md`.

## Terms

- Step: the `step` key of a task state `.temp/viber/<id>/state`, where the task stands for `ready`: `offered` (listed under `start:`, the state holding the mark and the step alone), `run` (a coder block was printed), `waiting` (after `NEXT: wait`), `held` (after `NEXT: hold`, until `repair`), `skipped` (the task and each dependent of a skip chain, set before its `--skip` call runs), `lost` (after a first `lost`, until `ready` lists the task) and `done` (after `commit 0`). A state with no such key reads `run`; one with no model (an offer, a skip mark) is no step state: `start` begins it at attempt 1 and any other event exits 2.
- Collision: one `coder FAIL --wait` return naming paths another task neither done nor skipped claims. A pair is the two tasks whichever of them waited, and one call is one collision of a pair however many paths of the claimant it names.
- Claimant: the first task in plan order, other than the waiting one and neither done nor skipped, whose `Files` or one of its two extras files lists the path. A skipped task never finishes, so it claims nothing.
- Free path: a named path with no claimant, a dirty file no task lists yet (a coder lists an extra file only at its return).

## Contracts

- `task-step.sh <plan> <subject> <started> <event>` answers each return of a task agent with blocks, each opening on `NEXT:`, `RUN:`, `ASK:` or `STOP:`: the body lines after it are sent verbatim in the dispatch the verb names, and an `add:` field names a line the model copies from the return it holds (`reason`, `repair`). The header defines every event, verb and field. It keeps the task state under the repository root, discarded when written under another `started:` mark, and the session lessons in `.temp/viber/lessons`; it takes no free text in its arguments and exits 2 with one `error:` line and an empty stdout.
- `ready` (subject `-`) answers one block, `NEXT: ready | start: <ids> | retry: <ids>` (a field left out when empty) or `NEXT: ready | none`, from what `task-ready.sh ready` lists: it hands the `offered` and `run` tasks as `--flight`, the `waiting` ones as `--waiting`, the `lost` ones as `--lost` and the `held`, `skipped` and `done` ones as `--held`, read from the state file of every task under the current mark, and marks every id it prints as in flight (`offered` for a `start:` id, `run` for a `retry:` id) before it answers, so a later call never lists it again. `implementor` reports `start` for each `start:` id and `retry coder --waited` for each `retry:` id. A `ready` that `task-ready.sh` refuses exits 2.
- `lost` (subject a task id: its coder or reviewer ended with no return at all) is answered by that same `ready` block and asks nobody. The state key `gone` counts the losses since the last PASS or FAIL return: the first loss of a task at step `run` sets the step `lost` (`gone=1`), so the block lists it under `retry:` once and `retry coder --waited` prints the same attempt's coder block again, with `reason: no return` when it has no ready reason line (`gone=2`); the next `lost` then ends the attempt as a coder failure with that reason line, answered by the next attempt's coder block, the hold or the cap arbiter, the task still in flight. A first loss while the reviewer is out (the state key `out` reads `reviewer` from a `NEXT: review` block until that reviewer returns or another block replaces it) is answered by the same round's `NEXT: review` block instead, the step still `run` and `gone=2`: the coder returned, so no coder goes out again. A `lost` while `gone` is 1, or for a task that is waiting, held, skipped or done, changes nothing; one for an offer nobody started removes its state, so the block lists the task under `start:` again.
- `task-ready.sh <plan> ready` lists a task under `start:` when it is neither done nor skipped, every `Depends-on` id is done, no sequenced line names an `<other>` for it that is neither done nor skipped, and it is in none of the four lists; a waiting task under `retry:` when no sequenced line holds it and none of the tasks its last wait named (the `wait:` and `free:` lines it wrote last, no line of another task between them) is in `--flight`; a lost task under `retry:` when no sequenced line holds it, whoever is in flight, and never while it is also in `--flight` or `--held`. The tasks in flight and the listed ones are at most 10 together, the retries first, then the starts, each in plan order. A task whose `Exclusive` line reads `true` is listed only when nothing is in flight and no other task can be listed, alone, a retry before a start; while one is in flight the answer is `none`. An id of the four lists that is done or skipped in `status.md` is dropped from them.
- `coder FAIL --wait "<path>[,<path>]"` runs `task-ready.sh <plan> wait <id> --flight <the offered and run tasks>` and answers per line it prints: `wait:` the block `NEXT: wait | on: <claimant>` (`on: <id>,<id>` for a free path: the other tasks in flight); `sequence:` the line `RUN: "<plugin root>/scripts/commit-task.sh" --decide "<plan>" "<id>" "sequenced after <claimant>: both need <path>"` then `NEXT: wait | on: <claimant> | sequenced`. With only `unclaimed:` or `blocked:` lines, or with `task-ready.sh` failing, the return is a plain `coder FAIL`. A wait ends no attempt.
- `task-ready.sh <plan> wait` prints, for a claimed path, `sequence:` with the first of its paths in the call when the waits file held a line of that pair before the call or the claimant is not in `--flight` (a retry sent at once would meet the same refusal), else `wait:`; `blocked: <path> | by: <claimant>` for a claimant that runs only after the waiting task (through `Depends-on` ids and sequenced lines, however many steps), which is not remembered: such a wait would never end. A free path is waited out once: one `wait: <id> | on: <id>,<id>` line naming the other tasks in `--flight`, the task going on `retry:` once all of them left flight; with no other task in flight, or on the second wait of that task on that path, it prints `unclaimed: <path>` and is not remembered, so the return is a plain coder failure.
- `.temp/viber/waits`: first line `started: <mark>` (a file under another mark is written again from its first line), then one `wait: <id> | <claimant> | <path>` line per remembered claimed path, one `free: <id> | <id>,<id> | <path>` line per remembered free path (the tasks in flight at that wait) and one `sequence: <id> | <claimant> | <path>` line per `sequence:` line printed. A sequenced line is `decision: <id>: sequenced after <other>: both need <path>` of `status.md`; a sequence line of the waits file counts as one in both modes, so the pair holds from the call that printed it, whenever its decision line is recorded.
- `retry coder --waited` prints the current attempt's coder block again, the attempt unchanged; a task with no ready reason line of its own carries `reason: waited on <paths>`, so its coder continues the work in the tree.
- `task-ready.sh` exits 2 with one `error:` line and nothing on stdout: unusable argv, a missing plan, a `wait` for an id the plan does not hold, a waits file that cannot be written. It reads the plan unchecked: `task-step.sh` has `plan-index.sh` check it first.
- `red-check.sh "<plan>" "<id>"` prints a `red-check:` line (`FAIL-AS-EXPECTED <log>`, `PASSED-WITHOUT-CHANGE <files>`, `NO-PRODUCTION-CHANGE <files>`, `UNRUNNABLE <reason>`) then a `NEXT:` line, with exit 0: `NEXT: review` after `FAIL-AS-EXPECTED`, `UNRUNNABLE` and `NO-PRODUCTION-CHANGE` (the red run passes and the task changes no production file: HEAD already holds the behaviour, so a coder attempt would rerun the same run), `NEXT: coder-failure | reason: tests pass without the change: <files>` after `PASSED-WITHOUT-CHANGE`, exit 2 on bad arguments or plan. `task-step.sh` takes that `coder-failure` as one only the first time for a task in a session (its state key `rcrej`), and sends every later one to review with the `red-check:` line. A linked directory (`node_modules`) is a real directory of one link per entry, an `@scope` directory likewise, never one link to the whole; an entry linking into a workspace package of the repository points at the worktree's own copy, so the red run loads HEAD's package code. Each directory holding links is listed in `red-check.owner` before it is made; the trap and the next run's recovery unlink every link entry of a listed directory first, then `git worktree remove --force` and `git worktree prune`, so the forced remove never reaches the main tree through a link.

## Commands

- The scheduling rules, in process: `node --test tests/viber/lib/task-ready.unit.test.ts`. The events of `task-step.sh`: the legacy pair `tests/viber/task-step.test.ts` (about 3 minutes) and `task-step.critical.test.ts`, whose fixture copies `task-ready.sh` and its entry beside the script.

## Change together

- The directive format of `task-step.sh`: its header defines it, `skills/implementor/SKILL.md` step 4 acts on each verb, `tests/viber/task-step.test.ts` pins it and `tests/viber/ready-prose.unit.test.ts` the scheduling events; the `NEXT:` words `red-check.sh` prints (`review`, `coder-failure`) are read by `task-step.sh`.
- The sequenced decision text `sequenced after <other>: both need <path>`: printed by `task-step.sh` on its `--decide` line, read back from `status.md` by `lib/task-ready.ts` and `lib/run-notes.ts`.
- The `WAIT:` line: `agents/task-coder.md` writes it (every path a `viber guard:` refusal named, and a dirty file outside its `Files`), `skills/implementor/SKILL.md` passes it as `--wait`, `lib/file-guard.ts` words the refusal that asks for it.

## Traps

- Never edit `task-step.sh` while its test runs: bash reads a script incrementally, so a header edit mid-run shows as a syntax error in the running cases.
- `ready`, `lost` and a skip chain write the step of other tasks than the subject, and under the mark `unknown` the states an earlier session left count for `ready` until `start` discards each.
- `task-ready.sh wait` with no `--flight` reads every claimant as not running and sequences each first collision: `task-step.sh` always passes the flag, the waiting task among its ids.
