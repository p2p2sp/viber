# viber/scripts - editing the GitHub comment and issue wrappers

Read for a change to `qa-comment.sh`, `pr-threads.sh`, `pr-reply.sh`, `issue-facts.sh` or `post-comment.sh`: what each posts or lists, and the grammar and stubs they share. The node holds the wrappers' common rules.

## Contracts

- `qa-comment.sh` posts on the run's issue, the frontmatter `issue:` of the `spec.md` beside the qa file, and on the `--pr` or same-repository branch pull request (a cross-repository one is never the target) only when the run has none. It posts at most once per run: the body's first line `<!-- viber:qa <path> -->` marks the run key (the qa file's parent directory name), and a comment already carrying the same key, from the run directory or its archive, yields `STATUS=skip`, `REASON=exists`.
- `pr-threads.sh` lists unresolved review threads (`THREAD=`) and the remarks outside them (`REMARK=`: each Conversation comment and each non-empty review body, numbered after the threads, key `comment-<id>` or `review-<id>`), and lists nothing (`REASON=wrong-branch`, no threads file) unless the checked-out branch is the pull request's head branch. A ready run replaces `.temp/viber/pr-feedback/<N>/threads.md`. A thread whose latest comment opens with the reply marker is left out and counted in `SKIPPED=`; a remark by the pull request author or a bot, or answered by a pull request comment opening with its marker, is left out and counted too; an empty remark or a Conversation comment opening with any viber marker is left out uncounted. A remark whose author has no account is listed. Only the first 100 threads, Conversation comments and reviews are read (`TRUNCATED=yes`).
- `pr-reply.sh` takes the key of the remark. A bare `<id>` (a thread's first comment) is answered through the `.../pulls/<N>/comments/<id>/replies` endpoint (GitHub has no reply to a reply); `comment-<id>` and `review-<id>` get one new pull request comment (`.../issues/<N>/comments`): the marker, the quoted first line of the original, its link, then the reply file. Each posts at most once: the body opens with the marker `<!-- viber:pr-feedback <key> -->` and a blank line, is kept in `.temp/viber/pr-feedback/<N>/posted/<key>.md`, and the newest thread reply opening with it, or any pull request comment opening with it for a remark, yields `STATUS=skip`, `REASON=exists`. A remark whose original cannot be read exits 1 and posts nothing. A relative reply file resolves from the cwd, unlike `qa-comment.sh`.

## Change together

- The issue reference grammar (`<N>`, `#<N>`, or `https://<host>/<owner>/<repo>/issues/<N>` with any `#...` fragment or `?...` query dropped) is parsed the same way in `issue-facts.sh` and `post-comment.sh`; `qa-comment.sh` applies it to the run's `issue:` and to `--pr` pull request URLs.
- The reply marker `<!-- viber:pr-feedback <key> -->` is matched in `pr-threads.sh` (its awk block) and written and matched in `pr-reply.sh`; the `--jq` output shape of each (`pr-threads.sh`: `R`/`Q` remark lines first, then `T`/`C`/`B` tab lines, with a header of `CMORE=`, `RMORE=` and `AUTH=`; `pr-reply.sh`: `<in_reply_to_id> <first body line>` for a thread, the original's url and first body line for a remark) is emulated by the stub of `tests/viber/pr-threads.test.ts` / `pr-reply.test.ts`, so a filter change changes the stub. The pull request reference grammar is parsed the same way in both.
