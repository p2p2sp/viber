Preparation

Installation and setup

/viber:setup: once per project and after every upgrade.

  • Installs from the p2p2 marketplace: claude plugin install viber@p2p2.
  • Creates .claude/viber.yml with a comment on every key.
  • Adds .temp/ and .claude/viber.local.yml to .gitignore when nothing ignores them yet.
  • Seeds the recommended permissions into .claude/settings.json, including a bare Bash allow.
  • Asks merge or reset when an existing settings.json differs.
  • Merge: viber's value wins a conflict, permission lists only grow, foreign keys stay untouched.
  • Merge moves a permission from deny to ask when viber moved it.
  • Reset: keeps a copy of the old file in .temp/viber/setup/.
  • Never touches .claude/settings.local.json.
  • Checks that the gh CLI is installed.
  • Checks that CLAUDE.md names: the build, the whole suite, a single test file, the fast command and the test layer marker.
  • Gives a ready prompt to paste when items are missing.
  • With no CLAUDE.md, points to /viber:memory.
  • Never edits CLAUDE.md.
  • Opens the guide in the browser.
  • Idempotent: a rerun merges in new switches and keeps the values you set.
  • Restores a deleted key of the planning, build, github and directories groups.
  • Moves a switch written outside its group into the right group.
  • Migrates an old true/false of build.baseline-tests to full/off.
  • Raises the file's schema: number, never lowers it.
  • viber.yml and .gitignore are only ever added to, never rewritten.

Configuration

The .claude/viber.yml file: 10 switches, model tiers, titles, directories, branching.

  • Switches in the planning, build and github groups; only true turns one on.
  • Without the file, every switch is off.
  • planning.adr: architecture decision records in docs/adr/.
  • planning.plain-plan-review: review of plans written without the planner.
  • planning.fast-path: a fast path for small changes.
  • build.baseline-tests: off, fast or full.
  • build.final-review: a review of the whole build after the last task.
  • build.memory: updates CLAUDE.md at the close of a build.
  • build.rules: updates .claude/rules/ at the close of a build.
  • build.qa: QA scenarios and an E2E handoff at the close of a build.
  • build.cleanup: archives the run with its summary.
  • build.extensions: a map of your own agents that close a build.
  • github.issues: work with GitHub issues.
  • tiers.min / tiers.max: the build's model range (haiku < sonnet < opus < fable).
  • fable runs only when the project names it.
  • Planning always runs on the session's model, outside the tiers range.
  • github.issue-title: the issue title pattern ({template-title}, {type}, {summary}).
  • github.pr-title: the pull request title pattern ({type}, {summary}, {issue-number}, {entry}).
  • directories.runs / directories.specifications: the run and archive directory names under docs/.
  • .claude/viber.local.yml: personal overrides of 4 keys, kept out of git.
  • Empty or invalid local values are ignored.
  • A session start warns when the project's schema: is older than the installed viber.
Input: from report to understanding

Research conversation

/viber:talk: talks one topic through with you before you decide anything.

  • Takes a topic or an opening thesis; with none, asks what to talk about.
  • A free exchange of views, not an interview: no numbered decisions, no option lists.
  • Takes a position on every thesis, yours and its own, with its reason.
  • Says plainly when you are wrong and rates ideas out of 10.
  • Brings counter-arguments, alternatives, costs and failure cases you have not raised.
  • Keeps its opinions labelled apart from facts.
  • Reads the code before claiming what the project does.
  • Every claim that carries weight goes to the researcher agent: versions, numbers, limits, prices, licences, what a tool or standard does.
  • Sources ranked: the vendor's own documentation and the standard's own text first, independent research next, named-author publications last.
  • Forum answers, content farms, AI summaries and marketing never carry a verdict alone.
  • Each claim comes back confirmed, refuted, disputed or unverified, with dated links.
  • A source older than the version a claim concerns counts only as history.
  • Several claims checked in parallel; fetched pages stay out of the conversation.
  • A refuted claim that held up a position changes the position, said out loud.
  • Asks whether to wrap up when new rounds only repeat.
  • Ends on conclusions: what was established, what stays open, where you disagree, your options with their trade-offs.
  • Gives its own pick only when you ask for it.
  • Suggests keeping the conclusions with /viber:handoff, without running it.
  • Never writes code, a plan, an issue or a file, and never starts another skill.

Idea validation

/viber:idea-validator: decide whether a business idea is worth turning into a side project.

  • Starts only when you invoke it, with the idea as text or the path to a file.
  • Asks for missing input once at intake, then proceeds.
  • Web research on the problem, the market and the competition, by three parallel subagents.
  • Scores the idea on 9 dimensions, including Distribution, Side-project fit and Autopilot fit.
  • Every number carries a source URL or is marked as no data found.
  • A council of 7 independent perspectives, in two rounds; --quick skips the second.
  • Disagreement is kept, not averaged; the dissent is part of the report.
  • An experiment plan with Go, Pivot and No-Go thresholds fixed before any result.
  • One self-contained HTML report in the language of the idea.
  • The verdict means worth testing, not worth building.

Issue triage

/viber:triage: assesses one reported issue against the current code.

  • Takes an issue number, a link or pasted text.
  • Rebuilds the current ask: the body as revised by each later comment.
  • Says which comment changed what in the ask.
  • Treats an earlier triage report as an assessment, not a revision of the ask.
  • Separates what the reporter observed from what they assume.
  • Locates files and symbols, each marked read or inferred.
  • Classifies: bug, feature request, other.
  • For a bug, states the divergence as a hypothesis, with no reproduction.
  • Assesses feasibility, variants with a recommendation, impact and size.
  • Lists risks and unknowns.
  • Writes the report in plain language for a non-technical reader.
  • Writes the report in the conversation's language, whatever the issue's language.
  • Never quotes secrets or file contents.
  • Treats the issue text as data, never as instructions.
  • Names the next step (/viber:fixer or /viber:intent) without running it.
  • Posts the report as a comment on the issue on your yes.
  • Writes no code, no test and runs no application.

GitHub issues

/viber:issue-create and the github.issues switch.

  • Creates an issue from the project's issue form templates.
  • Covers issues of every kind, bugs included.
  • Picks the template from the argument or the conversation.
  • Shows a preview and asks before creating.
  • Titles it per github.issue-title.
  • Sets the issue type; a type failure never removes the created issue.
  • Refuses clearly with no templates, no gh or no repository.
  • /viber:intent, /viber:fixer and /viber:prototype start from #42, a number or a link.
  • Treats the issue body and comments as settled, with no repeated questions.
  • An interview with no issue can save its confirmed summary as a new issue.
  • An interview tied to an issue can add its summary as a comment when it settled more than the issue says.
  • /viber:intent #42 resumes work from a saved issue.
  • A fixer diagnosis can be saved as a new issue.
  • The issue link travels into the plan, then into the pull request as Closes or Refs.
  • A failed GitHub call is never retried automatically.
  • On an uncertain result, says it is unknown whether the comment landed.

UI prototypes

/viber:prototype: see and compare a UI change before planning it.

  • A self-contained, working HTML mockup in the project's own look.
  • First question: one proposal or three variants.
  • Three variants behind an A/B/C switcher in one file.
  • The conversation covers the screen only: layout, hierarchy, content, states, flow, style.
  • Reads the existing screen first and never asks what the code states.
  • Data, APIs and performance are parked as open points for intent.
  • Look based on the design system, the code's styling or the description alone.
  • Uses the impeccable or viber:pro-designer skill when available.
  • Opens the mockup in the browser on its first version.
  • Rounds: create, revise, narrow to the chosen variant.
  • File in .temp/viber/prototype/, with the issue number in its name.
  • Exit: on to intent, a comment on the issue, or both.
  • You attach the mockup to the comment yourself in the browser.
  • The accepted mockup travels with the plan into the build as an attachment.
  • The coder of a task that names the mockup matches the screen to it (layout, content, states).
  • Never edits the project's code.

UI design standards

viber:pro-designer: professional UI and UX design standards that avoid generic, AI-looking interfaces.

  • Starts when the look of an interface is the goal: a new screen or page, a redesign, a UI review or critique.
  • Also starts on choices of colors, type, spacing, layout or motion, and on a UI that looks generic or AI-generated.
  • Does not start for a small functional change.
  • Reads its AI slop filter in full first, before proposing anything.
  • Names the visitor's success on the surface before any design decision.
  • A tell nobody asked for is out; a tell the brief pinned stays.
  • Optional contrast check with Node.js.

Planning interview

/viber:intent: turns an idea into a confirmed understanding for the planner.

  • Never starts on its own; suggested in one line, the decision is yours.
  • Alternative for simple changes: Claude Code's plain plan mode.
  • Never asks what the conversation or the code already says.
  • Opens with a line naming what it takes as settled.
  • When everything is settled: straight to the summary, zero questions.
  • One question per message, in prose.
  • Every question: 3 concrete options, the recommendation first.
  • Numbered decisions and options (2.1, 2.1.1) for a quick answer.
  • Questions in dependency order; each answer narrows the next.
  • Challenges weak reasoning and contradictions with the code out loud.
  • Plain language, no abbreviations or acronyms, in the user's language.
  • Order: problem, done condition, boundaries, requirements, unknowns.
  • Every unknown gets a way to resolve it.
  • Skips what a competent implementer decides alone.
  • Sizes the scope before the first detail question.
  • Proposes the spec shape: spec-full or spec-lite.
  • Escalates to spec-full past the sixth question.
  • A summary under 15 lines, to confirm or correct.
  • For a screen change with no mockup, offers "prototype first".
  • Draft mode: the plan stops at the specification alone, on your request.
  • Resuming a draft asks only about what the remarks changed.
  • --prove: the prover agent checks every question against the code and the web before you see it.
  • Hands off the summary verbatim, so it survives context compaction.
  • Never proposes end-to-end tests; only on your explicit request.

Large scopes and roadmap

An idea too big for one cycle, such as a whole application.

  • A scope above about 30 tasks is split before any detail question.
  • Cut by size alone, never by theme or milestone.
  • Every part holds about 8 tasks or more; smaller ones are merged.
  • Ordered parts: each one consumes only what earlier ones produced.
  • No stubs, mocks or temporary stand-ins between parts.
  • A part is not a release: no working application is required in between.
  • The interview covers every part in order.
  • A question hanging on an earlier part's code becomes an unknown of that part.
  • Every part gets its own plan and its own build.
  • roadmap.md holds the decisions and unknowns of later parts.
  • A finished build names the command for the next part.
  • Resuming asks only what the builds since changed.
  • The next part builds on the previous part's branch.

Fast path

planning.fast-path: a small change with no plan file.

  • Only a change in existing code, with no new subsystem or domain concept.
  • Limit: 2 tasks with code, 5 in total.
  • A short design in chat: what changes, in which files, how it is proven.
  • Builds only after an explicit "build it".
  • No plan file and no run directory.
  • The change is made in the current session, then tested by test-runner.
  • Red tests: repair and run again.
  • Exceeding the limit: stops and points to the full interview.
  • Ends by suggesting /viber:commit, never commits.
  • A request for a full plan returns to the regular interview.
  • Unavailable on a run branch and when resuming a draft or a roadmap.

Bug diagnosis

/viber:fixer: the root cause proven by a test, with no fix applied.

  • Traces the flow step by step with actual values, never "probably".
  • Stops at the first divergence: the cause, not the symptom.
  • Confirms the divergence produces the reported symptom.
  • Writes a reproduction test and actually runs it.
  • The test must fail on the defect, not on a typo or configuration.
  • The test sits at the narrowest level, usually a unit at the diverging layer.
  • A test that passes at once sends it back to tracing, never to a weaker assertion.
  • Test header: the cause, actual versus expected state, the fix direction.
  • The red test stays as evidence and as a regression guard.
  • Never applies the fix itself, not even a one-liner.
  • Diagnosis: cause, symptom link, test, fix direction, blast radius, done condition.
  • Asks you to choose when several fix approaches are defensible.
  • Skips the reproduction only with your explicit authorization.
  • The diagnosis is always a spec-lite, handed to the planner.
  • The planner marks the test as Repro:; the coder must turn it green unchanged.
Planning

Planner

Started by intent or fixer; writes the plan in plan mode.

  • Enters only with a confirmed interview or diagnosis.
  • Never reopens decisions the interview took.
  • File map first: what is created, modified, deleted.
  • Before the tasks, the impact-mapper agent finds every reference to what the change modifies, moves or deletes.
  • Adds nothing the interview left unsettled.
  • One responsibility per file; an unwieldy file may be split.
  • The specification (what and why) is kept apart from the tasks.
  • spec-full: problem, current behaviour, scenarios, edge cases, glossary.
  • Scenarios tagged NEW or CHANGED with the old behaviour.
  • A "Must not change" section: behaviours that must stay as they are.
  • spec-lite: goal, acceptance criteria, file map.
  • Tasks: dependencies, files, contracts, deliverable, verification, DoD, coverage, TDD.
  • C<n> contracts: data shapes shared between tasks.
  • Every acceptance criterion covered by a task.
  • Parallel tasks never share a file.
  • An acyclic, minimal dependency graph.
  • Widening a contract requires handling at every consumer.
  • TDD: required by default.
  • A task's verification is a concrete command, not the whole suite.
  • An Exclusive task for shared resources (a port, a database).
  • Every design choice settled in the task, so a sonnet coder makes none of its own.
  • A Hard line only on a task whose design cannot be settled in advance.
  • Designs a shared test harness when the project has none.
  • An integration test lives in the adapter's task, never on its own.
  • End-to-end tests only on explicit request.
  • A UI or endpoint change with no E2E: suggests /viber:e2e or build.qa.
  • The files the plan is built from (a mockup, a findings.md) as attachments: in its frontmatter.
  • A task that needs an attachment names it in its done clause; one that needs none names none.
  • Script validation: the rules tagged (script).
  • Review by the planner-review agent: the rules tagged (review), rounds until PASS.
  • Findings that need a decision reach you as a question.
  • Every write after a PASS voids it.
  • Shows the plan's full path and names the next step.
  • The plan survives a cleared context through its source: line.

Decision records (ADR)

planning.adr.

  • The adr-screener agent tests the plan's decisions against a strict admission test.
  • Exclusions: any one of them makes a decision no record.
  • Gates: all must hold, each with evidence.
  • Names the records to deprecate or extend.
  • An accepted record becomes a task with no dependencies writing docs/adr/.
  • The planner never adds or rewords a record of its own.

Plan gate and hooks

Four hooks and one module working behind every session.

  • Blocks leaving plan mode without a reviewer's PASS after the last plan write.
  • Compares the file's modification time with the verdict's time: an edit after PASS voids it.
  • Also catches edits made through sed -i or an editor.
  • A plan written without the planner needs a PASS from the plain-plan-review agent.
  • Every deny message opens with "Next step:" and the ready command.
  • Injects hints into a plan in plain plan mode.
  • Hints: a task list, parallel subagents, a closing review with fixes.
  • Loads viber's rule manifest into the context at session start.
  • The viber loaded <version> banner shown to the user.
  • Warns about an outdated schema: and the need for /viber:setup.
  • Blocks viber agents from mass-killing processes (killall, pkill, taskkill /IM).
  • Rescues agent report writes the harness blocks by file name.
  • Every hook fails open: an error never blocks work.
  • Manifest: no code before an approved plan.
  • Manifest: no branch unless asked.
  • Manifest: temporary files only under .temp/.
  • Manifest: questions with options always through a choice dialog, in the conversation's language.
  • Manifest: honest ratings of ideas, on a scale of 10.
Build

Build orchestration

The implementor builds an approved plan task by task.

  • Starts from the approved plan, with no text copied by hand.
  • Copies the plan into a dated run directory under docs/_specs/.
  • Detects other open runs and asks which one to build.
  • Refuses to build a draft with no tasks.
  • Validates, splits and commits the plan.
  • Every coder gets only its own task file.
  • Reads no file and writes no code itself: it only delegates.
  • Model choice: haiku for simple tasks, sonnet for ordinary ones, opus only for tasks the plan marks Hard.
  • Every model clamped into the tiers range.
  • Review waived only for sonnet tasks verified by the build or tests; a task whose contract three or more tasks use is reviewed on opus.
  • Dispatches every task whose dependencies are done, in parallel.
  • Never waits for a whole batch: unblocks the next tasks at once.
  • Exclusive tasks run alone, with nothing in the background.
  • A task list in the UI with the model and a [TDD] tag.
  • A commit after every task: T<n> - <title>.
  • A commit stages only the task's files, as exact paths.
  • Up to 5 attempts per task, each one model tier up.
  • Holds a task when another coder is changing a file it needs; no attempt is counted.
  • Files outside the task's map are added to its commit and recheck.
  • Code left untested is deferred to a later task to prove; with no later task, it gets a repair pass before the final review.
  • A task past its 5 attempts is held and gets a repair pass before the final review.
  • Coder notes passed to the tasks that depend on them.
  • The run is committed: resumes in a new session or on another computer.
  • A half-finished task: continue, start over or skip.
  • Changes no task claims: commit them separately or leave them.
  • Skipping a task also skips the tasks depending on it.
  • A refused tool call: a question to retry, skip, accept or abort.
  • An agent with no verdict gets one reminder.
  • An agent with background processes must stop them.
  • Measures the build's elapsed time.

Arbiter

Decides on your behalf where the build would otherwise stop.

  • Picks one option from a closed list, with a reason and a cost if wrong.
  • A task past 5 attempts, after its repair pass: accept unreviewed or skip.
  • A red baseline: continue.
  • A red final test run after 6 rounds: accept.
  • A failed recheck of the final review: commit the fix.
  • A commit refused after a retry: leave it uncommitted.
  • A coder stuck on a decision: picks one of its options.
  • The ruling binds later attempts and dependent tasks.
  • Every ruling goes into rulings.md.
  • Rulings listed in the final summary.

Task coding and review

The task-coder and task-reviewer agents and the TDD cycle the coder reads from references/tdd.md.

  • The coder delivers exactly what the task says, nothing more.
  • Files outside the map only when they block the DoD, and reported.
  • Respects contracts, "Out of scope" and "Must not change".
  • Runs only its own task's verification (the tree is shared).
  • Up to 5 repair rounds before failing.
  • Git read-only; removal through git rm.
  • Never commits, never branches.
  • Matches the style of the surrounding code.
  • A task rendering or styling an interface reads references/ui-tells.md, a short checklist of generated-UI tells, in the coder and the reviewer.
  • Notes of up to 8 lines: conventions, traps, doubts.
  • Returns options to unblock a task it cannot complete.
  • TDD: first a test that fails on an assertion.
  • TDD: one test per DoD clause, named after the behaviour.
  • TDD: minimal code to green, refactor only on green.
  • TDD: code written before its test is deleted.
  • TDD: no horizontal slicing, no mocking internals, no testing implementation details.
  • Resumed TDD adds the missing tests to existing code.
  • The reviewer gates the task against its definition.
  • Two levels: Blocking and Minor; a report only on Blocking.
  • Rechecks tasks whose files another coder changed.
  • A failure from before the build never counts against the task.
  • An arbiter ruling wins over the task file.

Tests in the build

The test strategy and the test-runner agent.

  • Four layers: unit, component, integration, e2e.
  • Every test carries its layer's marker.
  • Unit and component tests use no real external dependencies.
  • Component: the whole application in the test process, adapters as in-memory fakes.
  • Integration: one adapter against its real, disposable dependency.
  • Test containers preferred.
  • Unit and component tests far outnumber integration tests.
  • (blocking) rules bind the coder, the reviewer and the fixer.
  • A fast or full baseline before the first task.
  • The build repairs only the failures it caused.
  • The final test run happens exactly once.
  • Scope: the fast tests plus the integration tests the change reaches.
  • Integration tests selected by changed adapters, migrations and schemas.
  • The full integration layer and E2E stay in CI.
  • Commands from CLAUDE.md or the project's manifest.
  • Supports package.json, Makefile, pyproject.toml, .csproj, go.mod, Cargo.toml, composer.json.
  • A failed build: no test starts.
  • No tests in the project: a SKIP verdict.
  • The log stays out of the context; only failures reach the report.
  • A long suite runs in the background, with no call timeout.
  • A red run: a repair coder, up to 6 rounds.

Final review

build.final-review: what neither task review nor the tests can see.

  • After every task is committed, before the final test run.
  • Slices of at most 8 tasks, reviewed in parallel on sonnet.
  • Searches the whole repository for consumers of changed symbols.
  • Finds broken or stale consumers.
  • Finds references to removed things.
  • Finds additions nothing reaches.
  • Finds fixtures that no longer match what the code emits.
  • Finds criteria resting on skipped or unreviewed tasks.
  • One coder fixes everything, Blocking and Minor, in one pass.
  • A reviewer rechecks the fix.
  • Every fix described in the summary: what was wrong, what changed.
  • Matters no code change settles reach you as OWNER: lines.
  • No opinions on style or naming.

Build close

Steps after the final test run: memory, rules, QA, extensions, archive.

  • Memory: updates the CLAUDE.md nodes below the root.
  • Root changes only as suggestions.
  • Rules: confirmed conventions written into .claude/rules/.
  • Memory and rules in one chore commit.
  • QA: written on sonnet; qa.md with scenarios to perform by hand.
  • QA: every scenario opens with a checkbox the tester ticks once it is performed.
  • QA: qa.e2e.md for automation through /viber:e2e.
  • qa.md posted as a comment on the run's issue, or on the branch's open pull request when the run has none, once per run.
  • Project extensions run in order, optionally in parallel.
  • Every extension committed separately.
  • Records drift: what was delivered beyond the specification.
  • The build summary in outcome.md.
  • Archive in docs/specs/: specification, scenarios, rulings, attachments, summary.
  • Plan, status, tasks and notes dropped in one commit (git keeps them).
  • Closing screen: the result, tests and elapsed time, then one sentence saying whether outcome.md records a problem.
  • Summary without an archive: at most 7 lines plus fixes and rulings.
  • On a run branch with no roadmap part left: asks whether to open the pull request through /viber:pr-create.
  • Suggests the command for the next roadmap part.
  • Uncommitted paths and skipped tasks named in the summary.

Branching

The branching: group and BRANCHING.md.

  • Modes: off, allowed, required.
  • Several kinds of branch, each with a base, a name pattern and a pull request target.
  • Name patterns: {type}, {slug}, {issue-number}.
  • The issue type picks the kind of branch (issue-type-mappings).
  • Settled when the interview or diagnosis starts, before any code is read.
  • No question when exactly one entry fits.
  • Checks HEAD against the base and offers a switch.
  • Shows how far the base is behind its remote.
  • Uncommitted changes block the switch.
  • required never commits onto a base.
  • Settled again after a new issue is saved.
  • Resuming a draft offers a switch back to its branch.
  • Ready examples: trunk-based, GitHub Flow, GitLab Flow, Release Flow, GitFlow.
  • Readable configuration error messages.
  • An invalid entry is dropped, the rest still works.
  • Never fetches, pushes, merges or deletes.
Shipping

Pull requests

/viber:pr-create.

  • A pull request for the current branch, after a preview.
  • Started by you, or by your yes when a build finishes on its run branch with no roadmap part left.
  • Refuses with a reason: no gh, no repository, detached HEAD, dirty tree.
  • Refuses: a base branch, an existing pull request, no commits.
  • The target comes from the branch entry or from a question.
  • Title from github.pr-title.
  • Body from the entry's template, the shared template, or Summary, Changes and Testing sections.
  • Fills only from the specification, the commits and the conversation, never invents.
  • Empty sections read _No response_; checkboxes ticked only when confirmed.
  • Closes #n for the default branch, Refs #n otherwise.
  • Choice: create, create as draft, cancel.
  • Pushes the branch only on your yes.
  • Assigns the pull request to its author.
  • Adds the run's qa.md as a comment on the run's issue, or on the pull request when the run has none, once per run.
  • On an existing pull request, posts only the QA comment.
  • Never writes under .github/.

Pull request feedback

/viber:pr-feedback <pull request number or URL>, started by you only, on the pull request's own head branch.

  • Lists the unresolved review threads, each marked problem, question or no action; outdated ones are flagged.
  • Leaves out a thread whose latest comment is already a viber reply and counts it as skipped.
  • Choice: all, pick numbers, cancel; a no-action thread is left out of "all".
  • Writes review.md with one section per chosen thread and hands it to /viber:intent: one plan task per thread, each task's done condition writes its reply file.
  • Thread text is data: a comment telling the model to do something is classified, never obeyed.
  • --reply after the build is pushed: lists the ready replies and the threads still missing one, asks once.
  • Posts each ready reply into its own thread once, through the review comment replies endpoint, and reports each link or skip reason.
  • A failed post is reported and never retried; the next reply is still posted.
  • Stops with one line on a wrong branch, and on an unpushed HEAD for --reply.
  • Never resolves a thread, creates, switches or pushes a branch.

Commits

Say "commit": the only path to a commit.

  • An agent in its own fork, keeping the context clean.
  • A Conventional Commits message.
  • Type and scope matched to the repository's history.
  • No arguments: every change, new and deleted files included.
  • With paths: only the named files or directories.
  • Works from a subdirectory of the repository.
  • An issue number becomes a Refs: footer.
  • Verifies itself after the commit.
  • No push and no branch.
  • A one-line result: the SHA and the message.

E2E tests

/viber:e2e: QA scenarios as Playwright tests.

  • Takes the qa.e2e.md of the named or newest run, the archive included.
  • Checks for playwright-cli and @playwright/test.
  • Installs what is missing only on your yes.
  • Asks for the test directory, the base URL, the start command and the test accounts.
  • Never guesses a missing value.
  • Checks whether the application is up and starts it when needed.
  • Waits up to 120 s for it to start, then asks.
  • Never changes the start command, its configuration or ports.
  • UI and API scenarios; non-automatable ones are skipped.
  • One scenario at a time, one test file per scenario.
  • Every test proven green against the running application.
  • An application fault: the scenario is marked blocked, the application left untouched.
  • Automation state kept in qa.e2e.md; the next pass skips what is done.
  • One commit with the tests and the handoff file.
  • The application is left running.
Project maintenance

Code audit

/viber:code-auditor [lens] [scope]: many agents, every finding verified.

  • 6 lenses: bugs, security, web-performance, runtime-performance, tests, design.
  • The performance and quality groups ask which lens.
  • Scopes: changes (diff), from a commit (diff:<sha>), a directory, the whole repository.
  • Asks for whatever parameter is missing.
  • Phases: Frame, Map, Hunt, Verify, Synthesize.
  • The mapper reads the project's memory, git history and the lens's signals.
  • The map: conventions, history, severity calibration, units.
  • Scouts cheaply score units past the budget.
  • A hunter investigates one unit or one lens angle in depth.
  • Budget: one hunter per angle (diff), 8 (directory), 16 (repository).
  • At most 16 agents at once.
  • A critic independently tries to refute every finding.
  • The critic never sees the hunter's reasoning.
  • Lenses that run code do so on a clean checkout.
  • On the diff scope, uncommitted changes are laid over the clean checkout.
  • Deduplication by root cause, not by file.
  • Severity 0 to 10, confidence, a VERIFIED, PARTIALLY VERIFIED or INCONCLUSIVE verdict.
  • findings.md: up to 10 full entries, the rest in a further-findings list.
  • An entry: root cause, reproduction, fix sketch.
  • Coverage notes: units not investigated, hunts with no result.
  • A variant wave: the same class of defect elsewhere.
  • With a confirmed finding, ends on the next step /viber:intent <path of findings.md>, which attaches it to the plan.
  • Never edits code.
  • Every defect class has one owner lens; the others hand it over by name.
  • The code-auditor README.md: every lens, its angles, how it verifies and what it hands over, for people.
  • Bugs: wrong results, silent failures, crashes and hangs from any input, races and data integrity, contract mismatches, variants of past fixes.
  • Bugs: listeners, timers and subscriptions never released on the error path or on unmount.
  • Security: injection, access control, authentication, untrusted data into machinery, secrets, cryptography and supply chain.
  • Security: prompt injection into an LLM or agent holding tools, secrets or other users' data.
  • Web performance: JS weight, LCP, layout stability, hydration, assets and delivery.
  • Web performance: server-rendered and plain HTML sites, with no JavaScript framework, included.
  • Runtime performance: complexity, I/O per item, unbounded growth, blocking hot paths, repeated setup, query shape.
  • Runtime performance: ReDoS, uncapped request bodies and uploads, missing timeouts, uncapped retries, unbounded fan-out.
  • Tests: pseudo-tested code, hollow assertions, over-mocking, untested error paths, flaky tests, dead tests.
  • Tests: a stray .only or skip silencing a critical suite reaches the top severity.
  • Design: knowledge duplication with a copy-paste detector, change preventers, wrong abstractions, boundary coupling, dead code and drift, rule drift.
  • Design: verification gates scoped to each angle.

Skill and agent authoring

viber:skill-designer: authoring doctrine for Claude Code skills and agents.

  • Starts when a skill or agent is created, refactored, split, audited or tuned for a model.
  • Also starts when you ask to shrink an existing SKILL.md or choose model: or effort: for one.

Reliability and portability

Rules shared by skills, agents and scripts.

  • Every script works in Git Bash on Windows and on macOS.
  • GitHub scripts in plain POSIX sh.
  • Scripts print self-verifying KEY=value blocks.
  • Script refusals carry distinct exit codes.
  • One configuration parser, which always succeeds.
  • Every agent ends on a verdict; a refused tool call becomes a question.
  • Agents sharing the tree never use stash, checkout or restore.
  • Exact paths in commits, bracketed segments included (App Router).
  • .temp/ files never reach a commit.
  • Background processes stopped before an agent ends.
  • Switch-dependent text loaded only when its switch is on.
  • Works for projects of every kind, untestable ones included.
